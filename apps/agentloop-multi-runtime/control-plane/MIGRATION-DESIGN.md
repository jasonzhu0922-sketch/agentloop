# Control-plane migration boundary (WP-1)

`cp_*` schema ownership belongs to the standalone Admin control-plane migration job. In TiDB, schema means database: Admin uses a dedicated `agentloop_admin` database, separate from Router and Runtime databases. The executable migration is source-level in `admin-api/src/persistence/control-plane-migrations.ts`, with a separate `cp_schema_migrations` ledger and checksum; no Router/Runtime migration or `mr_*` table is reused.

The job accepts only an explicit TiDB `AGENTLOOP_ADMIN_DATABASE_URL` pointing at the dedicated Admin database. `npm run provision:admin-database -- --apply` creates that database; `npm run migrate:control-plane` is dry-run by default; use `npm run migrate:control-plane -- --apply` only after choosing the exact target database. It owns only: `cp_resources`, `cp_releases`, `cp_target_assignments`, `cp_apply_receipts`, `cp_integration_bindings`, `cp_skill_artifacts`, `cp_secret_references`, `cp_credential_grants`, `cp_integration_invocations`, `cp_audit_events`, and `cp_delivery_cursors`. Grant and invocation tables retain opaque IDs, hashes, binding/release references, secret version metadata and stable result codes only; no credential value, access token, endpoint or result payload is stored.

SQLite, PostgreSQL, and TiDB retain source-level DDL contracts and in-memory/dialect tests. The Admin API only checks the ledger with `assertControlPlaneMigrationsReady`; Admin API, Router, Cloud Host, and Local Agent startup paths never create these tables.
