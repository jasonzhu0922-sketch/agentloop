# 从问题到受控 SQL

规划由当前 Agent 完成。元数据、查询与分析按需要穿插；简单问题不必为了满足流程而增加模型轮数。

场景选择是前置用户决策，不属于领域推断。开始规划前必须已有本任务中用户明确指定的场景或已接受的场景选择 HIL。仅有“销售额”“员工人数”等业务词，或某场景看起来唯一相关，都不能作为选择授权；缺失时先执行 `select-scenario` 并等待，不跨场景探查来替用户决定。

## 意图与领域绑定

为每个目标确认指标定义与单位、对象范围、时间范围、筛选条件、分组粒度和排序/比较集合。将这些语义绑定到目录中的来源、字段、指标公式和时间规则。记录会改变结果的假设，不能让用户未要求的示例或目录建议变成强制筛选。

先读场景索引，再取相关表详情；本 Run 已取得的完整且版本一致的目录直接复用。SQL 前简要确认会影响本题结果的口径：指标及单位、必要筛选、维度与粒度、时间字段及边界、表与关联键。简单问题可直接在规划中表达，不要求额外交付一张“口径卡”。未确认的状态条件不能照抄其他案例。

- **对象身份：** 用户简称与数据库存储的名称未必相同。优先查目录中的别名、实体编码及关系；需要探查时先对用户给定线索查询 DISTINCT 名称与编码，确定候选后再读取相关指标项目，不把所有名称或全部报表行当作身份定位的输入。包含匹配只能发现候选，不能证明所有匹配组织都应该相加。父组织、分支与总部可能重叠，未确认层级时分别呈现。
- **指标含义：** 相似项目名不自动等价。先检查值域与指标定义，确认人数、金额、比率及单位。行数、去重实体数、业务报表项目值是不同指标。不得将不同报表项目或不同层级混加。
- **期间：** 按目录编码转换用户日期，区分自然月、财务月、月末快照与累计值。快照通常不跨期相加；同比/环比必须有可比区间。
- **关系与粒度：** 仅使用已确认的关系。先检查主从关系与重复风险，再决定去重或预聚合。独立来源并列比较不要求 JOIN；不得因缺少关系而臆造公共键。

## SQL 与错误恢复

使用明确的 TiDB/MySQL `database.table` 和字段，参数占位符为 `%s`，参数单独传递；不把参数值拼入 SQL。只查询当前问题必要的数据：实体和项目确定后，单值问数筛选对应期间、实体与项目，不读取整份报表再从中复述其他指标。探查结果须注明探查范围，LIMIT 过的候选列表不能声称完整。`allow_output=false` 的原始字段不直接输出；服务端仍会独立校验。

本入口使用 PyMySQL 的 `%s` 参数数组约定，目录标明 `database_engine=tidb`、`sql_dialect=mysql`。日期示例：`sale_date >= CAST(%s AS date) AND sale_date < CAST(%s AS date)`，对应独立参数 `["2026-06-01", "2026-07-01"]`；不要使用 PostgreSQL 的 `::date`、`ILIKE`、`DATE_TRUNC` 或 `$1/$2`。MySQL 日期截取使用 `DATE_FORMAT`，日期运算使用 `DATE_ADD`/`DATE_SUB`；模糊匹配使用 `LIKE`，需要忽略大小写时按真实排序规则或 `LOWER` 明确处理。`DATE '2026-06-01'` 是 SQL 字面量语法，不能套成 `DATE %s` 或 `DATE $1`。绑定失败不证明日期参数不可用，也不能成为内联用户值的理由。

目录足以支持目标 SQL 时，直接执行有业务目的的查询。`SELECT 1` 没有引用授权表，会按策略拒绝；不以此检查连接，也不机械执行全表 COUNT、MIN/MAX 或不含目标期间的分布。仅在缺失事实会影响口径或结果解释时做最小探查，保留必要过滤条件。

先根据领域计划生成 SQL。策略拒绝时读拒绝原因并修正不合法引用或操作，不绕过限制；执行失败时根据目录、错误代码与 SQL 定位，无法确定就说明失败。空集合和 NULL 不等于 0：先区分筛选未匹配、项目缺失或源数据为空，再决定有依据的探查或澄清。

恢复先看 `error.diagnostic.phase/code`。`query.bind` 下的 `unsupported_parameter_style` 或 `parameter_count_mismatch` 是请求参数错误，按 `%s` 与参数个数修正；业务 SQL 尚未提交。`query.explain`、`query.execute`、`result.fetch` 属于不同执行阶段；有 TiDB/MySQL `vendor_code` 时据此定位，无代码或无原始错误证据时不得断言是参数、字段、VPN 或数据问题。不重复执行同一已知失败组合，不通过删掉业务筛选使查询“成功”。

核对按风险选择：JOIN 可能放大度量时，按实际主从粒度检查去重或预聚合；`COUNT(*)` 和 `COUNT(DISTINCT 订单主键)` 可以不同，不能要求一单只有一条明细。分组合计与独立总量只在口径一致且可加总时比较，不累加比率或重叠实体。日期边界由字段类型、条件与目录口径决定，不能用演示数据的均匀分布或总行数比例证明。已有结果能确定性核对时直接计算，不固定增加多条核对 SQL。

涉及多条查询时分别保留请求和结果，按依赖顺序执行；无需为了修正单条 SQL 重新执行已成功的查询或整套流程。
