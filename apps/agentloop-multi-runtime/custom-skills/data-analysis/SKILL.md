# 数据查询与分析

## 业务范围

- **集团经营分析（`group`）**：财务报表项目查询与组织、期间对比；经营指标实际值、计划值、完成情况与差异分析；人力月报项目及员工人数查询、趋势与组织对比；钢联行情指标和历史走势；采购合同数量、金额与分布分析。
- **采购销售库存（`demo`，演示数据）**：客户与供应商、销售与采购合同及订单、产品与原料库存、生产计划与消耗、质检、发货、应收应付和收付款查询分析。演示结果不得作为真实集团经营事实。

上述范围对应当前接入场景；实际可用表、指标、组织层级、时间粒度和关联关系以所选场景的当前目录为准，不据此跨场景查询或承诺目录未提供的指标。场景选择要求见下文工作流。

完整问数链路属于本 Skill，由当前 Agent 使用当前会话模型完成业务判断。包内包含目录读取、SQL 校验、场景隔离、只读执行、审计、结果保存和可选 HTTP 接口的全部实现；不依赖另一个项目的代码或服务，不启动另一套模型流程。不调用自然语言整链路 `/api/runs`、`/api/runs/stream` 或 MCP `query`。规划、SQL、修正、工具结果和结论保留在当前 Runtime Run 中。

场景目录、指标、术语、关系、分析方法与查询审计均存于 TiDB；业务查询也直接访问 TiDB。数据源定义与凭据由宿主在 Skill 根目录 `connections.json` 配置，连接使用 `tidb://`。使用 Runtime 提供的 `python3` 直接执行本包 `scripts/data_client.py`；脚本沿用启动它的解释器，依赖见 `requirements.txt`。无需用户提供项目路径或设置 `NL2SQL_PROJECT_ROOT`。配置仅由脚本读取，不回显凭据，不要求用户粘贴连接密码。通常无需启动 HTTP 服务。

## 工作流

1. **先取得用户明确的场景选择。** 用户必须以场景 id、场景名称或本任务的结构化 HIL 选择明确指定场景。用户未指定时，首先执行 `scripts/data_client.py select-scenario --output <workspace-file>`；该动作读取真实场景目录，输出标准 HIL 单选控制结构，由 Runtime 持久化并暂停当前 Run。等待用户选择后才能读取任何场景元数据、规划或执行 SQL；即使只有一个场景也必须确认。不得根据问题内容、数据相关性、默认配置或模型判断自动选择，不得以普通文字询问或展示 JSON 代替实际 HIL。用户已在本任务明确指定或通过 HIL 选择的场景有效，无需重复询问；先用目录校验其身份，精确绑定选择的 id，其他任务或其他 Run 中的选择不能自行沿用。元数据与查询始终显式传 `scenario_id`；用户改变选择时立即按新选择执行，不混用旧场景证据。HIL 结构及恢复规则见 [数据访问契约](references/input-contract.md)。
2. **理解问题并查目录。** 明确对象、指标含义、时间、输出粒度及比较范围。先用 `catalog --scenario-id <id> --question <用户问题> --output <workspace-file>` 保存业务索引；优先读取 `/retrieval`、`/matched_terms` 及命中定义，按缺失信息再取指标/术语索引或候选表摘要，不批量读取全部摘要。选源后用 `--source-id <表> --question <用户问题>` 保存详情，读取本题所需的指标、实体、期间定义和适用限制，再按 `read_contract.source_fields` 精确取 SQL 所需字段，不默认读取整张表的全部列描述。已有完整且版本一致的定义直接复用；缺少依据时再扩展读取。排序不代替判断，也不排除低分表或必要关联表。摘要未准备或已过期时依据当前物理字段和已有定义继续核实，不凭旧摘要断定缺少数据。使用真实字段、指标、术语、值域、关系、实体和期间编码，不把示例或简称当成真实字段值。目录足以生成目标 SQL 时直接查询，不机械执行连接探针、全表计数或无时间筛选的分布。具体读取方式见 [数据访问契约](references/input-contract.md) 与 [规划与口径](references/planning.md)。
3. **制定领域计划。** 依据 [规划与口径](references/planning.md) 将问题绑定到表、字段、时间编码、指标公式、项目条件、组织编码和输出粒度；使用指标的 `expression/project/grain`、术语的 `meaning/aliases`、`entities` 和 `period_formats`，保留来源及核验状态。针对具体组织/对象问数时，把 `matched_terms` 中命中的术语解释成规范名称，使用 `resolve-entity` 按本表实体定义查证编码，将返回的 `query_plan` 随实际取数 SQL 提交（可用 `--query-plan <解析结果文件>`）；取数回执的 `plan_verification` 必须确认 SQL 的本表编码条件与所选编码一致。没有实体定义时按规划参考中的缺定义路径核查，不能伪造绑定。摘要线索不能覆盖人工口径或用户明确要求，目录可读不代表生成的 SQL 已满足定义。用户指标只有相近候选且选择会改变口径时，先通过结构化 HIL 确认，不静默替换指标。采用正式指标或明确期间时，在同一个 `query_plan` 加入 `metric_bindings` 和 `time_bindings`，随 SQL 同次提交；执行器按当前定义核对项目值与存储期间边界。计划无需独立模型轮或新增工具调用。只按已确认的关系与粒度 JOIN；独立来源分别查询。缺失业务定义才澄清，目录或小范围探查能确定的事实由你查证。
4. **生成并执行 SQL。** 由你按目录声明的 TiDB/MySQL 方言生成 SQL，通过 `scripts/data_client.py execute --request-json` 在同一次工具调用中传入 SQL 和独立参数数组，无需中间请求文件。统一使用 `%s` 占位符；日期需要转换时使用 `CAST(%s AS DATE)`，不使用 PostgreSQL 的 `::date`、`$n` 或 `DATE %s`，不因一次绑定失败改为拼接值。执行前确认筛选值和聚合含义，使用目录中的 `database.table`。包内执行器强制执行 SQL 策略、场景授权、数据库表级只读权限、输出字段限制、超时、结果大小限制与审计。不自行写另一套数据库连接或读取连接密码来绕过执行器。
5. **核对与修正。** 检查状态、`plan_verification`、实际 SQL 和完整数据集。回执 `content_complete=true` 时响应在 `/content`；`dataset_complete=true` 时完整数据集在回执 `/dataset`。否则按 `read_contract.file_pointers` 读取保存文件：文件根就是原响应，行在 `/dataset/rows`，没有 `/content` 层。先读取回执指明的根和键，不猜 `/sources` 或 `/fields`。空集合、NULL、策略拒绝和执行失败是不同结果。先读 `error.diagnostic` 的阶段与代码，再做针对性修正；诊断不充分时标明未确定，不靠删除必要条件或反复更换占位符猜测。意外空值时核对对象、值域、期间与项目，必要时进行最小只读探查，依据证据修正 SQL。核对按任务与 JOIN 风险选择，优先在现有结果中完成；不固定追加全表计数、状态覆盖和总量查询。不要重复查询来恢复预览省略的数据，不把故障改写为无数据。
6. **分析并交付。** 按下文回复规则直接回答用户问题。趋势、比较等任务再按需使用目录中的方法与 [分析方法](references/analysis-methodology.md)，通过可复核的代码或 SQL 计算；主动判断图形是否有助于理解，适合时在最终回复中直接使用 Runtime 声明支持的 Markdown 图表格式展示，不只描述“可以画图”或返回数据文件。每个数值和实体描述对应具体结果行或计算输出，无法定位的内容不作为事实交付。完整数据保存在结果文件中，以场景、`query_id`、目录版本、SQL 和文件引用在当前 Run 内保留证据链，按用户需要提供追溯信息。

## 回复规则

- 默认先给业务结论，详略随问题复杂度决定。单值问数通常一两句话，包含数值、单位、日期和必要的主体限定；来源用简短业务名称即可。用户要求明细、趋势或对比时再展开表格或图表。
- 只解释会改变答案或影响解读的口径、歧义和限制，例如价格类型不同、多个主体数值不同、缺失目标日期或采用替代日期。多项指标数值相同不能据此认定口径相同或互相验证；保留有业务意义的区别即可。
- 查询过程与核对留在内部，不默认附加“口径说明”“数据可得性”“证据链”“局限”等固定章节，也不罗列排除的候选、无关覆盖期或通用免责声明。确有影响结论的问题时，在答案旁简短说明。
- `query_id`、`catalog_revision`、SQL、物理表名、结果文件路径及工具回执属于内部追溯信息；用户要求 SQL、来源明细、审计或排障时再按所需范围提供。用户要求的数据文件或报告仍正常交付。

## 证据与执行边界

- 用户问题决定目标，元数据和查询结果约束事实。目录中的方法建议不能自行增加用户未要求的业务条件。
- 字段值域与本次 DISTINCT 观测范围不同；组织别名、层级与合并口径需要证据，不猜等价、不混加报表项目或层级。
- 工具结果通过 Runtime 正式 Result 保留；跨步骤消费继承的 ResultRef 时使用 `read_result`，不要靠步骤摘要重建证据。完整响应或完整小数据集已内联时直接使用；其他情况按回执指针读取完整文件或确定性计算，不因读取预览省略而重复查询。只看部分排序记录不能证明对象不存在。
- `dataset.row_count` 必须与完整 `rows` 一致；超过结果上限时明确失败，不交付未声明的部分成功。查询回执只证明执行事实，不能证明业务回答正确。
- `connections.json` 只作为脚本配置输入，不加入报告、工具参数或日志。连接或依赖不可用时指出具体阻塞，不询问无关项目路径、不改宿主授权、不启动替代服务、不降级直连。
- 本包按场景隔离，不提供用户级认证。每个业务场景使用仅有授权实体表 SELECT 权限的独立账号；目录账号只能读取场景配置并追加查询审计。TiDB 不支持 `START TRANSACTION READ ONLY`，不启用伪实现的 no-op 开关，使用真实数据库权限、SQL 策略、查询超时和结果限制共同约束执行。HTTP 接口仅监听本机；只有用户明确要求 HTTP 形式时才启动包内服务。数据源业务数据只读，唯一数据库写入是配置目录数据库的查询审计表，不写业务表、不修改配置、不初始化数据库。
