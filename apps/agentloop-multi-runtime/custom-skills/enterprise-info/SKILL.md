# Enterprise Info — 企业信息查询

查询中国大陆企业的工商注册信息，包括企业主体、统一社会信用代码、法定代表人、注册资本、经营范围、联系方式及关联登记信息。

## 配置

只读取本 Skill 根目录的 `.env`。部署时将同目录 `.env.example` 复制为 `.env`，填写 `ENTERPRISE_INFO_API_BASE_URL`、`ENTERPRISE_INFO_API_CLIENT_ID` 和 `ENTERPRISE_INFO_API_CLIENT_SECRET`；API 地址必须使用 HTTPS。

不读取 Runtime/Local Agent 的 `.env`、全局环境变量或外部配置路径。缺少文件或必填项时明确报错。真实 `.env` 不进入 Git 或分发 ZIP，不要读取或回显凭据到模型上下文、日志或交付物。每次部署或安装后，在实际执行的 Skill 根目录维护此文件。

## 适用情形

用于企业查询、工商信息、营业执照、法人、注册资本、经营范围、股东、主要人员和分支机构等问题。需要查询的企业必须有名称、简称或足以识别的线索；没有时先请用户补充。

不用于海外企业、通用编程或文档制作。

## 查询原则

- 以实时查询返回为准，不凭训练记忆补全事实。
- 确认的是查询对象，不以相似名称或关联企业替代。
- 保留用户要查的具体职务、时间和口径。工商登记字段是来源事实，不能自动替代公司公告、董事会聘任或官网管理层口径；查询当天不等于任职信息的生效日或最新更新日。

## 查询流程

1. 先查询与用户输入相符的候选企业。候选结果只用于识别主体，不能作为工商详情或最终答复的依据。
2. 没有候选时，请用户补充名称、地区或其他可识别线索；恰有一个候选时，继续查询该企业的具体信息；有多个候选时，只呈现可选择的候选并等待用户确认，不输出候选中的简略登记字段。
3. 用户确认后，必须将所选 option 的完整 `label` 原样作为 detail 或 personnel 的 `name`，并将该 option 的 `identityRefs[0]` 作为 `identity-ref`。不得缩写、截断或根据名称相似性替换为母公司、分公司或关联主体。

### 已确认选择的接续约束

恢复上下文中出现 `agentloop.humanLoopResolution/v1` 的 `selectedOptions`，或出现同一查询步骤的已提交精确选择时，该选择已经完成主体识别：所选 `label` 和 `identityRefs[0]` 是最终、不可重新解释的 detail 或 personnel 输入，不是需要再次验证的候选线索。

- 已确认的主体直接用于所需的登记查询：需要登记人员证据时使用 personnel，需要基本登记信息时使用 detail。不要为找回、确认或重新解释这个已选主体而重新搜索或再次发起相同的 HIL 选择。一次登记查询完成不代表用户目标完成；所问事实仍有缺口时，继续使用适合该事实的已授权来源。
- 不得以名称相似性将选择替换为母公司、分公司或关联主体；也不得要求用户重复选择已经确认的同一候选。
- detail 或 personnel 的返回身份若与 `identity-ref` 不同，或详情不可用，这是详情查询的冲突/不可用结果，不是重新打开原候选列表的理由：不得交付错误主体，也不得重复原 HIL。保留冲突证据并如实说明所选主体当前无可用详情。只有后续任务确实需要用户在一组**新的、实质不同的**可选主体中做选择时，才可以发起新的 HIL。

`detail` 和 `personnel` 的两个输入共同构成主体绑定：`name` 用于上游 API 查询，`identity-ref` 用于验证 API 实际返回的主体。候选搜索得到唯一结果时，也应将该候选的 `credit_no` 作为 `identity-ref` 传入；不要只凭名称继续查询。

### 人员证据与查询范围

需要工商登记主要人员作为证据时：

- 使用 `enterprise-info-query` 的 `personnel` action，不能以通用 `detail` 的工商概览或“主要人员示例”代替完整取数。
- `personnel` 返回 API 的完整工商登记主要人员列表作为证据；用户要求名单时，逐项交付姓名和登记职务。只问具体职务时，先针对这些职务给出有依据的答案，不用整张人员表替代回答；没有对应字段时明确说明缺口。
- 不把工商登记“主要人员”擅自扩大为该公司的全部内部领导班子；如用户要的是组织任命口径、党委班子等，说明本 Skill 的登记口径并请求或检索相应权威来源。
- 指定职务、现任高管或公司领导问题不自动变成登记名单查询。根据所问事实选择证据；主体已明确且官网或任免披露能直接回答时，不必为使用本 Skill 额外查询工商库。

### 指定职务与现任信息

- “总裁”“总经理”“董事长”“法定代表人”分别核验，不因名称接近、同属高管或某人兼任其他职务而推定等同。接口仅有“董事兼总经理”时，只能确认该登记职务，不能改写成“总裁”。
- 用户问现任职务时，登记数据先作为线索和有明确口径的证据；使用当前 Run 授权的公开检索能力核验公司官网管理层、交易所公告或最新任免披露，核对主体、原文职务、披露时间、生效时间及是否已有后续变更。不要为已确认的主体重复发起选择。
- 未能核验所问职务时，保留已证实的登记事实，明确哪个职务及其现任状态尚未确认；不得用记忆、相近职务或旧任免记录填满答案。没有可用的核验能力时，直接说明证据范围。
- 来源候选文本或 `deliveryCandidate` 是可用材料，最终答复仍须按用户问题综合。被审核否决后按缺口补证或改写，不要再次原样提交人员表。

## 交付

`detail` 按实际返回字段组织企业基本登记信息、经营范围和联系方式。股东、人员、分支和变更等关联信息默认给出可读摘要；用户明确要求人员/领导名单时，使用 `personnel` 而不是从 `detail` 摘要中自行推断或摘取示例。

不显示未返回的字段，不把来源事实扩展为法律、授信、交易或合规结论。涉及这些用途时，提醒用户以登记机关或权威登记系统的正式记录为准。

具体职务查询的最终答复应先逐项回答所问职务，再注明来源、数据日期及口径。区分来源的 `check_date`、实际检索日期与任职生效时间；来源没有提供的日期不自行补全。资料冲突时分别列明来源与日期并说明未解决之处。
