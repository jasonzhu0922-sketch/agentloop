# Enterprise Info — 企业信息查询

查询中国大陆企业的工商注册信息，包括企业主体、统一社会信用代码、法定代表人、注册资本、经营范围、联系方式及关联登记信息。

## 适用情形

用于企业查询、工商信息、营业执照、法人、注册资本、经营范围、股东、主要人员和分支机构等问题。需要查询的企业必须有名称、简称或足以识别的线索；没有时先请用户补充。

不用于海外企业、通用编程或文档制作。

## 查询原则

- 以实时查询返回为准，不凭训练记忆补全事实。
- 确认的是查询对象，不以相似名称或关联企业替代。

## 查询流程

1. 先查询与用户输入相符的候选企业。候选结果只用于识别主体，不能作为工商详情或最终答复的依据。
2. 没有候选时，请用户补充名称、地区或其他可识别线索；恰有一个候选时，继续查询该企业的具体信息；有多个候选时，只呈现可选择的候选并等待用户确认，不输出候选中的简略登记字段。
3. 用户确认后，必须将所选 option 的完整 `label` 原样作为 detail 的 `name`，并将该 option 的 `identityRefs[0]` 作为 detail 的 `identity-ref`。不得缩写、截断或根据名称相似性替换为母公司、分公司或关联主体。

### 已确认选择的接续约束

恢复上下文中出现 `agentloop.humanLoopResolution/v1` 的 `selectedOptions`，或出现同一查询步骤的已提交精确选择时，该选择已经完成主体识别：所选 `label` 和 `identityRefs[0]` 是最终、不可重新解释的 detail 输入，不是需要再次验证的候选线索。

- 立即且只执行一次 detail：用这两个原样字段调用 detail，然后根据 detail 结果交付。不要为找回、确认或重新解释这个已选主体而回读先前搜索结果、重新搜索、读取原始候选文件，或再次发起相同的 HIL 选择。
- 不得以名称相似性将选择替换为母公司、分公司或关联主体；也不得要求用户重复选择已经确认的同一候选。
- detail 的返回身份若与 `identity-ref` 不同，或详情不可用，这是详情查询的冲突/不可用结果，不是重新打开原候选列表的理由：不得交付错误主体，也不得重复原 HIL。保留冲突证据并如实说明所选主体当前无可用详情。只有后续任务确实需要用户在一组**新的、实质不同的**可选主体中做选择时，才可以发起新的 HIL。

`detail` 的两个输入共同构成主体绑定：`name` 用于上游 API 查询，`identity-ref` 用于验证 API 实际返回的主体。候选搜索得到唯一结果时，也应将该候选的 `credit_no` 作为 `identity-ref` 传入；不要只凭名称继续查询。

## 交付

按实际返回字段组织企业基本登记信息、经营范围和联系方式。股东、人员、分支和变更等关联信息默认给出可读摘要；用户明确要求某一类明细时，再围绕该类信息查询和呈现。

不显示未返回的字段，不把来源事实扩展为法律、授信、交易或合规结论。涉及这些用途时，提醒用户以登记机关或权威登记系统的正式记录为准。
