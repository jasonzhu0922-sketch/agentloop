# ODS 单表建模分析

对指定的 ODS 数据表做**面向 DDM 建模**的最小必要分析，输出结构化 Markdown 报告。

> **AgentLoop 接入边界**：仅允许通过已审批的 `ontoflow-jtbc` MCP 执行 `SELECT` 或 `WITH` 开头的只读查询。不得执行 INSERT、UPDATE、DELETE、MERGE、DDL、存储过程或多语句 SQL；没有实际查询证据时，不得将推断表述为表事实。

该技能不是做"大而全"的技术巡检，而是回答 6 个建模核心问题：

1. 这张表表达的业务对象是什么
2. 这张表的数据粒度是什么
3. 这张表的逻辑主键或业务唯一标识是什么
4. 这张表与哪些直接关联表存在关系
5. 这张表有哪些关键业务字段
6. 这张表是否可直接进入业务对象候选模型

适用于对 DB2 ODS 层数据表进行结构、样例、关系和建模可用性分析。

> **协同网络**：ODS 数据资源盘点（网络 5）
> - 成员：DB2 资产目录 ODS 导出技能（上游导出）、本技能（中游分析枢纽：消费导出数据 → 产出分析报告）、ODS 分析报告结构校验技能、ODS 分析报告质量检查技能（配套质检）、ODS→DDM 建模全流程技能（下游产出收数标准）、全域公共维度统计与合并分析技能（全域下游，产出公共维度清单）
> - 一致性约束：本技能产出的 Markdown 报告结构须与建模技能的输入解析一致；样本报告（references/sample-report.md）章节结构为结构校验技能的比对基准；核心原则/报告模板/输出规范为质量检查技能的检查依据
> - 变更同步：本技能改报告结构 → 同步建模技能输入解析与结构校验技能比对基准；改强制规则 → 同步质量检查技能检查项
> - 跨网络衔接：本技能产出的单表特征报告 → 网络 6 部署技能构建 graphify 知识图谱（tp-search 检索服务）；建模技能消费该图谱辅助业务域建模

## 核心原则

### 1. 最小必需

只保留建模真正需要的信息，不输出无助于对象识别的大段背景内容。

### 2. 事实与推断分离

- **查询事实**：必须来自实际 SQL 查询结果
- **建模推断**：如逻辑主键、父子关系、对象类型判断，必须显式写出"推断依据"

### 3. 单表为中心

报告围绕当前表展开，不做 Schema 级总览，不做跨域宏观分析。

### 4. 关联表适度展开

只保留 2~10 张最直接相关的表，避免把同前缀所有表全部堆进正文。当一张表确实应该有不少关联关系时，上限可定为 20 张。

### 5. 优先服务建模

优先保留对象识别、粒度判断、关键字段、关系、样例、状态分布；性能优化、运维治理类建议仅在必要时保留。

### 6. 命名业务化

逻辑实体名和属性名必须表达业务语义，不直接照搬物理表名或字段名。命名、字段类型或关系判定不确定时，读取 `references/logic-entity-modeling-rules.md`。

### 7. 字段类型显式判定

关键字段必须区分为：数据类型字段、主标识字段、外部引用字段、准标识字段。字段名包含 `ID`、`UUID`、`CODE`、`NO`、`NAME` 时，必须结合样例值体系判断，不能只凭字段名下结论。

### 8. 关系必须可验证

同前缀表只是候选，不等于真实关联。报告中的直接关联关系必须给出字段级关联条件和 SQL 验证依据，不要写成已确认关系。

> **强制验证规则**：所有候选关联关系 MUST 通过 SQL `INNER JOIN` 或 `EXISTS` 命中验证。除非当前分析表的数据记录数为 0，否则不得在最终报告中保留“待验证”状态。验证后只输出最终结论——命中则写“已验证（命中 N 条）”，未命中则写“无关联关系”。不得在报告中展示中间验证过程。

## 分析流程

严格按以下 4 步执行，每步必须等待上一步结果返回后再执行下一步。不可跳步，不可在没有结构信息前直接做业务结论。

所有 SQL 查询通过 Runtime 已绑定的数据资产只读查询能力执行，参数 `data_domain` 根据用户指定的数据域确定。Runtime 负责将能力解析到当前已授权的 ToolSource；若用户未指定数据域，必须先询问用户确认。

### Step 1：查询表结构基础信息

同时执行以下 4 条 SQL，获取当前表的基础定义：

**SQL-0 权威列数**（必须执行）：
```sql
SELECT COLCOUNT
FROM SYSCAT.TABLES
WHERE TABSCHEMA = '{schema}' AND TABNAME = '{table}'
```

> SQL-0 的 COLCOUNT 值是总列数的**唯一权威来源**。不要通过人工计数 SQL-1 返回的行数来确定总列数。

**SQL-1 列定义**（必须执行）：

> **分页规则**：设 BATCH_SIZE = 80。若 SQL-0 的 COLCOUNT ≤ 80，执行 1 条查询即可；若 COLCOUNT > 80，按 OFFSET 递增分多批执行，每批 OFFSET = 0, 80, 160, ... 直到 OFFSET ≥ COLCOUNT。总批次数 = ceil(COLCOUNT / 80)。

每批执行（替换 `{N}` 为当前批次的 OFFSET 值）：
```sql
SELECT COLNAME, TYPENAME, LENGTH, SCALE, NULLS, DEFAULT, REMARKS
FROM SYSCAT.COLUMNS
WHERE TABSCHEMA = '{schema}' AND TABNAME = '{table}'
ORDER BY COLNO
OFFSET {N} ROWS
FETCH FIRST 80 ROWS ONLY
```

**SQL-1c 列定义行数验证**（必须执行）：
```sql
SELECT COUNT(*) AS COLUMNS_ACTUAL_ROWS
FROM SYSCAT.COLUMNS
WHERE TABSCHEMA = '{schema}' AND TABNAME = '{table}'
```

> 将 SQL-1c 的 COLUMNS_ACTUAL_ROWS 与 SQL-0 的 COLCOUNT 对比：
> - 一致 → 列定义完整，继续分析
> - COLUMNS_ACTUAL_ROWS < COLCOUNT → SYSCAT.COLUMNS 返回不完整，以 COLCOUNT 为准，标注风险

**SQL-2 精确记录数**（必须执行）：
```sql
SELECT COUNT(*) AS TOTAL_ROWS
FROM {schema}.{table}
```

**SQL-3 索引信息**（必须执行）：
```sql
SELECT INDNAME, COLNAMES, UNIQUERULE
FROM SYSCAT.INDEXES
WHERE TABSCHEMA = '{schema}' AND TABNAME = '{table}'
ORDER BY INDNAME
```

本步骤必须产出以下判断：

- 当前表中文含义
- 总记录数（来自 COUNT(*)）与总列数（来自 SQL-0 SYSCAT.TABLES.COLCOUNT，不得人工计数 SQL-1 的行数）
- 是否存在显式主键/唯一索引
- 候选逻辑主键
- 是否存在明显的状态字段、时间字段、对象标识字段、关联字段
- 关键字段初分组：数据类型字段、主标识字段、外部引用字段、准标识字段
- 共性审计字段的规范化命名候选，如记录创建时间、记录修订者、记录归档标记
- **列覆盖清单**：根据 SQL-1 结果，按以下**结构化语义角色**分组列出全部列名，各组列数之和必须等于 SQL-0 的 COLCOUNT。若总数不匹配，说明有列在上下文压缩中丢失，必须重新执行 SQL-1：

  | 角色分组 | 定义 | 识别方式 |
  |:---|:---|:---|
  | **标识字段** | 唯一或近唯一识别当前实体实例 | 主键、唯一索引列、业务单号、UUID 格式值；不可为 NULL |
  | **引用字段** | 引用其他实体实例的外键 | 字段名以 `_ID`/`_CODE` 结尾且值体系指向外部对象；关联验证时能匹配到目标表主标识 |
  | **分类/状态字段** | 描述实体分类、状态、类型的枚举字段 | GROUP BY 分布统计呈现有限枚举值（通常 < 30 种）；REMARKS 含"状态""类型""标志""分类""标识" |
  | **度量字段** | 数值型业务指标 | TYPENAME 为 DECIMAL/NUMERIC/INTEGER/BIGINT/FLOAT；REMARKS 含"金额""数量""比例""费率""价格""成本""保证金" |
  | **时间字段** | 业务时间或系统时间 | TYPENAME 为 DATE/TIMESTAMP/DATETIME |
  | **描述字段** | 自由文本或展示文本 | TYPENAME 为 VARCHAR/CLOB 且非标识/非分类；REMARKS 含"名称""描述""地址""备注""说明""条件" |
  | **审计字段** | 记录行级生命周期信息 | 字段名或 REMARKS 含 CREATED/MODIFIED/UPDATED/DELETED/ARCHIVED/IS_DELETED |
  | **租户/组织字段** | 多租户或组织隔离 | 字段名或 REMARKS 含 BOOK/GROUP/ORG/DEPT/COMPANY/TENANT/PUR_ORG |
  | **扩展/预留字段** | TEMP/EXT/预留风格字段 | 字段名含 TEMP/EXT/RESERVED/SPARE；或无 REMARKS 且字段名无明确业务语义 |
  | **其他字段** | 未归入以上分组的字段 | 逐一列出，标注 REMARKS，供人工判断归属 |

> **分类规则**：
> - 不能仅凭字段名关键词分类——必须结合 REMARKS（字段注释）、TYPENAME（字段类型）和值体系（样例值）综合判断
> - 一个字段可能符合多个分组 → 按优先级归入最高组：**标识 > 引用 > 分类/状态 > 度量 > 时间 > 描述 > 审计 > 租户/组织 > 扩展/预留 > 其他**
> - 列覆盖清单总数必须 = COLCOUNT，不匹配时重新检查 SQL-1 结果完整性

### Step 2：查询直接关联表

先查同系列表，再从中筛选 2~10 张最相关的表（当一张表确实应该有不少关联关系时，上限可定为 20 张）。

**SQL-4 同系列表列表**（必须执行）：
```sql
SELECT TABSCHEMA, TABNAME, COLCOUNT, REMARKS
FROM SYSCAT.TABLES
WHERE TABSCHEMA = '{schema}'
  AND TABNAME LIKE '{prefix}%'
  AND TYPE = 'T'
ORDER BY TABNAME
```

> `prefix` 建议取"去掉末尾编号后的业务前缀"，例如：
> - `T_ODS_TCBYH0301` → `T_ODS_TCBYH`
> - `T_ODS_T_ACACM1` → `T_ODS_T_ACACM`

然后从同系列表中筛选 2~10 张**直接相关表**（当一张表确实应该有不少关联关系时，上限可定为 20 张），筛选时不能只看表名前缀，必须综合字段语义、字段类型、样例值体系和 SQL 命中结果。优先级：

1. 父表 / 头表
2. 明细表 / 子表
3. 维表 / 主数据表
4. 评分表 / 状态表 / 配置表

ODS 表如果存在同一系统的部署实例或环境后缀（如 `BSPD`、`BSWW`、`SHGX`），候选关系优先尝试同后缀表之间的关联，再考虑无后缀主表。

**SQL-5 直接关联表列定义**（必须执行，查 2~10 张，当一张表确实应该有不少关联关系时可查至 20 张）：
```sql
SELECT COLNAME, TYPENAME, LENGTH, REMARKS
FROM SYSCAT.COLUMNS
WHERE TABSCHEMA = '{schema}' AND TABNAME = '{related_table}'
ORDER BY COLNO
```

本步骤只需说明：

- 直接关联表是谁
- 可能通过哪些字段关联
- 当前表在关系链中的角色
- 候选关系是否属于外部引用字段 -> 主标识字段、主标识字段 -> 主标识字段、准标识字段关系
- **候选关系必须通过 SQL JOIN 命中验证**。除非当前分析表记录数为 0，否则每条关联关系均需执行字段级 JOIN 查询。命中则写"已验证（命中 N 条）"，未命中则写"无关联关系"，不得保留"待验证"状态

### Step 3：查询样例数据与关键分布

**SQL-6 关键业务样例**（必须执行）：

```sql
SELECT {关键业务字段逗号分隔}
FROM {schema}.{table}
{可选 WHERE 条件}
ORDER BY {优先时间字段或业务排序字段} DESC
FETCH FIRST 10 ROWS ONLY
```

字段选择原则：对象标识字段、时间/期间字段、状态字段、关键金额/指标字段、关键关联字段、必要的审计字段。

对 `ID`、`UUID`、`GUID`、`CODE`、`NO`、`NAME`、`ENAME` 等标识类或准标识字段，必须抽取 1~5 个非空样例值，用于判断：

- 字段更像主标识、外部引用、准标识，还是普通业务编码
- 值体系是否为 UUID、业务单号、状态码、类型码、路径、名称或展示文本
- 是否与候选关联表的目标字段值体系一致

**SQL-7 关键分布统计**（执行 1~3 个）：

```sql
SELECT {分类字段}, COUNT(*) AS CNT
FROM {schema}.{table}
GROUP BY {分类字段}
ORDER BY CNT DESC
```

优先统计：状态字段、年度/月度/会计期字段、主体字段/对象类型字段。

本步骤目标不是全面数据 profiling，而是支撑以下判断：

- 数据粒度是否稳定
- 状态值是否清晰
- 期间快照还是事务流水
- 是否具备稳定对象边界

### Step 4：整理并输出建模分析报告

根据以上查询结果，按下方报告模板整理，输出为 Markdown 文件。

> 报告"二、关键字段"的章节划分应沿用列覆盖清单中的语义角色分组，根据实际表的字段分布灵活组织，不必硬套固定章节名。例如：没有引用字段的表可省略该节；度量字段多的表可拆分"金额字段""比例字段"等子节；扩展字段只有 1-2 个时可并入"其他字段"。

输出文件路径：`{output_dir}/{schema}_{table}_分析报告.md`

**报告完成后必须执行列覆盖率自检**：

1. 统计报告中"二、关键字段"和"三、扩展与预留字段"章节出现的唯一字段名数量，记为 `REPORT_COL_COUNT`
2. 计算覆盖率 = `REPORT_COL_COUNT / COLCOUNT`
3. 在报告基本信息表中追加一行：

| **字段覆盖率** | REPORT_COL_COUNT / COLCOUNT（XX%） |

4. 如果覆盖率 < 90%，必须在报告"风险与缺口"中列出未被覆盖的列名及原因
5. 覆盖率不足时，优先补全业务属性字段，审计字段和扩展字段可在摘要中汇总

## 输出规范

- 使用 Markdown 输出完整报告
- 报告必须围绕**单张表**展开
- 表的列数量必须精准，字段必须全部列出
- 总列数必须来自 `SYSCAT.TABLES.COLCOUNT`（SQL-0），不得通过人工计数 `SYSCAT.COLUMNS`（SQL-1）返回行数替代
- 如果 SQL-1 返回的行数与 SQL-0 的 COLCOUNT 不一致，以 COLCOUNT 为准，并在报告中标注差异
- 关键结论必须区分"查询事实"和"建模推断"
- 必须包含 ASCII 关系图
- 必须包含样例数据（FETCH FIRST 10）
- 必须包含 1~3 个关键分布统计
- 不要把所有字段机械平铺，只保留建模关键字段
- 不要默认展开所有同前缀表，只保留 2~10 张直接关联表（当一张表确实应该有不少关联关系时，上限可定为 20 张）
- 不要把同前缀表直接写成已确认关系；必须给出字段级关联条件和 SQL JOIN 验证依据，不得在最终报告中保留"待验证"（除非当前表为 0 行）
- 不要默认逐条展开所有 TEMP 字段；仅展开有业务意义的字段
- 关键字段必须标注字段类型：数据类型字段、主标识字段、外部引用字段、准标识字段
- 标识类字段必须结合样例值体系判断，不能只凭 `ID/UUID/CODE/NO/NAME` 字段名下结论
- 共性审计字段优先规范化为记录创建时间、记录创建者、记录修订时间、记录修订者等口径
- 精确记录数必须来自 `COUNT(*)`，不要用 `SYSCAT.CARD` 替代
- 每一步 SQL 必须通过 Runtime 已绑定的数据资产只读查询能力获取实际结果
- 若字段含义、状态码或占位值不明确，标注"待补数据字典/业务口径"
- 若系统备注为空，基于字段名和样例数据自行判断对象语义
- 报告末尾标注生成时间和数据来源

## 注意事项

- 不要凭记忆回答表结构，所有结论必须有查询依据
- 如果无法确认逻辑主键，必须明确写"待验证"，不能直接断言
- 如果外键不存在但业务字段可关联，应写"逻辑关联"，不要写成"显式外键"
- 如果样例数据受权限限制，应注明样例范围，不要把局部样例误写成全量事实
- 对于列名、字段注释或状态值的业务含义不明时，应标记"待补数据字典"
- 如果表为空（0 行），在报告中如实说明，并在风险项中标注数据缺失风险
- 不要通过肉眼计数 SYSCAT.COLUMNS 的返回行数来确定总列数；总列数以 SYSCAT.TABLES.COLCOUNT（SQL-0）为准
- 所有候选关联关系必须通过 SQL JOIN 命中验证后输出最终结论（已验证/无关联关系）；仅当当前分析表为 0 行时可跳过验证；不得在报告中展示中间验证过程

## 批量分析模式

当用户要求批量分析多张表时：

1. 从用户提供的任务文件或表清单中提取所有待分析表
2. 每张表独立执行上述 4 步流程，产出独立报告
3. 可使用并行 Agent 加速批量处理
4. 每个并行 Agent 负责一组相关表（如按前缀分组）
5. 批量任务文件格式参考 `references/batch-task-format.md`
