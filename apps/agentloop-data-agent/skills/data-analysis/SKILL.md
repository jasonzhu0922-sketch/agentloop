# 数据查询与分析

## 业务范围

- **集团经营分析（`group`）**：财务报表项目查询与组织、期间对比；经营指标实际值、计划值、完成情况与差异分析；人力月报项目及员工人数查询、趋势与组织对比；钢联行情指标和历史走势；采购合同数量、金额与分布分析。

本 Skill 固定服务 `group`（集团经营分析）。实际可用表、指标、组织层级、时间粒度和关联关系以 group 的当前目录为准，不承诺目录未提供的指标。

完整问数链路属于本 Skill，由当前 Agent 使用当前会话模型完成业务判断。包内包含目录读取、SQL 校验、场景隔离、只读执行、审计、结果保存和可选 HTTP 接口的全部实现；不依赖另一个项目的代码或服务，不启动另一套模型流程。不调用自然语言整链路 `/api/runs`、`/api/runs/stream` 或 MCP `query`。规划、SQL、修正、工具结果和结论保留在当前 Runtime Run 中。

场景目录、指标、术语、关系、分析方法与查询审计均存于 TiDB；业务查询也直接访问 TiDB。数据源定义与凭据由宿主在 Skill 根目录 `connections.json` 配置，连接使用 `tidb://`。使用 Runtime 提供的 `python3` 直接执行本包 `scripts/data_client.py`；脚本沿用启动它的解释器，依赖见 `requirements.txt`。无需用户提供项目路径或设置 `NL2SQL_PROJECT_ROOT`。配置仅由脚本读取，不回显凭据，不要求用户粘贴连接密码。通常无需启动 HTTP 服务。

## 工作流

1. **直接使用集团经营分析。** 本 Skill 的场景范围已固定为 `group`，用户无需在提问中重复指定场景，也不再触发场景选择 HIL。目录、实体解析和 SQL 执行统一传 `--scenario-id group`；声明的执行动作已绑定该参数。若用户明确要求其他场景，说明当前 Skill 仅支持集团经营分析，不自行更换连接或扩展查询范围。实体、指标或口径有歧义时，仍按后续规则确认。
2. **先检索知识并定位数据源。** 明确用户的指标、对象、期间和输出粒度，用 `retrieve-knowledge --scenario-id group --request-json '{"question":"原始问题"}' --output <workspace-file>` 检索 TiDB 中维护的业务目录；先看 `sources.items`、`terms`、`metrics.items`、`ambiguities/gaps`。结合术语解释、命中理由与业务适用范围选择候选表，检索结果不自动确认口径。需要扩展时使用 `search-tables`，找指标使用 `search-metrics/get-metrics`，查表内列使用 `search-columns/get-columns`；分页未读完不证明对象或指标不存在。选源后优先一次调用 `get-query-context`，请求含 `question`、`source_ids`、检索返回的 `catalog_revision`，使用正式指标时同时传 `metric_refs:[{source_id,metric_id}]`，需要特定字段时传 `columns:[{source_id,names:[字段名]}]`。该动作只核对选中表的真实结构，补齐指标依赖、实体、期间、关系与必要字段，返回完整定义、来源、表签名和 `plan_seed`。已有版本一致的上下文直接复用；缺少字段再批量补取，不读取全部表、全部列或全部定义。`stored_snapshot_only` 表示仅检索了维护目录，SQL 前使用 `selected_sources_live` 的上下文。表摘要、业务定义或字段缺失时按诊断核实；不要把未命中当成无数据。动作与 JSON 示例见 [知识检索与精准元数据接口](references/retrieval-contract.md)，业务解释见 [规划与口径](references/planning.md)。
3. **制定领域计划。** 依据 [规划与口径](references/planning.md) 将问题绑定到表、字段、时间编码、指标公式、项目条件、组织编码和输出粒度；使用指标的 `expression/project/grain`、术语的 `meaning/aliases`、`entities` 和 `period_formats`，保留来源及核验状态。针对具体组织/对象问数时，把 `matched_terms` 中命中的术语解释成规范名称，使用 `resolve-entity` 按本表实体定义查证编码，将返回的 `query_plan.entity_bindings` 原样合并到 `get-query-context.plan_seed` 后随实际取数 SQL 提交；取数回执的 `plan_verification` 必须确认 SQL 的本表编码条件与所选编码一致。没有实体定义时按规划参考中的缺定义路径核查，不能伪造绑定。摘要线索不能覆盖人工口径或用户明确要求，目录可读不代表生成的 SQL 已满足定义。用户指标只有相近候选且选择会改变口径时，先通过结构化 HIL 确认，不静默替换指标。采用正式指标或明确期间时，在同一个 `query_plan` 加入 `metric_bindings` 和 `time_bindings`，随 SQL 同次提交；执行器按当前定义核对项目值与存储期间边界。从 `get-query-context.plan_seed` 继续领域绑定，原样保留 `catalog_revision/source_signatures`；仅采用正式指标时保留相应 `metric_bindings`，有具体对象和期间时再补实体及时间绑定。`period_formats` 是字段编码定义，不能直接复制为 `time_bindings`；查询最新月份等物理事实使用受限 `probe`。裁决与计划仍在同一个 Skill 步骤，不新增模型链路。只按已确认的关系与粒度 JOIN；独立来源分别查询。缺失业务定义才澄清，目录或小范围探查能确定的事实由你查证。
4. **生成并执行 SQL。** 由你按目录声明的 TiDB/MySQL 方言生成 SQL，通过 `scripts/data_client.py execute --request-json` 在同一次工具调用中传入 SQL、独立参数数组和完整计划；可用 `--query-plan <计划文件>` 传计划。统一使用 `%s` 占位符；日期需要转换时使用 `CAST(%s AS DATE)`，不使用 PostgreSQL 的 `::date`、`$n` 或 `DATE %s`，不因一次绑定失败改为拼接值或删除计划。执行前确认筛选值和聚合含义，使用目录中的 `database.table`。包内执行器强制执行单条只读 SQL 策略、场景授权表范围、输出字段限制、超时、结果大小限制与审计；连接账号的权限范围由宿主配置，不因其具有写权限、角色或转授权权限而拒绝目录读取和查询。不自行写另一套数据库连接或读取连接密码来绕过执行器。
5. **核对与修正。** 检查状态、`plan_verification`、实际 SQL 和完整数据集。回执 `content_complete=true` 时响应在 `/content`；`dataset_complete=true` 时完整数据集在回执 `/dataset`。否则按 `read_contract.file_pointers` 读取保存文件：文件根就是原响应，行在 `/dataset/rows`，没有 `/content` 层。先读取回执指明的根和键，不猜 `/sources` 或 `/fields`。空集合、NULL、策略拒绝和执行失败是不同结果。先读 `error.diagnostic` 的阶段与代码，再做针对性修正；诊断不充分时标明未确定，不靠删除必要条件或反复更换占位符猜测。意外空值时核对对象、值域、期间与项目，必要时通过受限 `probe` 探查，依据证据修正 SQL。核对按任务与 JOIN 风险选择，优先在现有结果中完成；不固定追加全表计数、状态覆盖和总量查询。不要重复查询来恢复预览省略的数据，不把故障改写为无数据。
6. **分析并交付。** 按下文回复规则直接回答用户问题。趋势、比较等任务再按需使用目录中的方法与 [分析方法](references/analysis-methodology.md)，通过可复核的代码或 SQL 计算；主动判断图形是否有助于理解，适合时在最终回复中直接使用 Runtime 声明支持的 Markdown 图表格式展示，不只描述“可以画图”或返回数据文件。每个数值和实体描述对应具体结果行或计算输出，无法定位的内容不作为事实交付。完整数据保存在结果文件中，以场景、`query_id`、目录版本、SQL 和文件引用在当前 Run 内保留证据链，按用户需要提供追溯信息。

## 方案 C 业务裁决与执行顺序

**保留原题并裁决候选。** 在本次 Run 的工作区保存原题原文和逐项必需条件：主体、指标、期间、币种或其他筛选、计算方式、去重键、结果粒度、required_outputs。每项记录原文 span、当前目录或实体查证依据、候选、淘汰理由、计划字段和待核对的答案标签。`decide.question` 与 `question_coverage` 都是模型提交的文本，只能作为线索；`plan_verification.status=verified` 仅证明列出的物理绑定，不能证明原题覆盖或答案正确。若 `question_coverage` 有 `unresolved` 或 `conflict`，回到原题和当前目录重选候选并重编完整计划。没有独立依据时保持未证实，不能把草稿冲突当成 enforce 的新硬拒绝。

**按错误性质修复。** `error_domain=conflict` 表示计划与 SQL 或现有定义已证实冲突，先判断错的是候选计划还是 SQL；`unproven` 表示当前校验器不能证明合法性，可尝试现有受控等价写法，或拆成各自带完整计划、参数、Gateway 和审计的查询；`input` 与 `catalog` 分别修输入和查目录；安全、权限和资源拒绝不得绕过。只有会改变答案、且目录和受控探查无法决定的真实业务选择才发 HIL。每次查询前声明结果粒度与 required_outputs，成功后逐项核对回执、ResultRef、主体、期间、单位与最终文字。Run 后续失败时先检查已完成查询和 ResultRef，再说明已取得与未取得的数据；不得声称未执行的写操作已完成。

**先判定是否需要继续。** 读取当前目录与一次有目的的受限探查后，若用户所需指标、组织层级、比较基期、公式或来源口径仍有多个会改变答案的合法选择，立即发起原生业务 HIL；不要用重复查表、猜项目名或反复修改计划消耗 Run 轮次。若目标期间严格晚于已核实的来源最大期间，或完整计划的正式查询对目标实体、指标和期间返回空集，直接说明该范围无记录以及派生量不可计算。若目录没有用户要求的正式指标，先查明确同名的报表项目；仍无定义时说明目录缺项，不能把相近指标当作它，也不能为了找一个答案无限扩大检索。

**按诊断和进展修正。** 初次 `query_plan` 是模型依据当前目录提出的候选合同，可能选错源、指标、比例语义或期间。`validate_plan` 只核对该合同的已声明物理条件与 SQL，不能证明它覆盖原问题。执行拒绝后先看 `error.diagnostic`：若合同仍符合原问题和最新证据，仅修该字段的 SQL；若新目录、实体查证、受限探查或用户澄清否定了合同，就重新取得 `get-query-context`、重新 `decide` 并重建完整计划，不为迎合旧计划改 SQL，也不为迎合 SQL 任意改计划。重建须保持原题必需的主体、指标、期间及筛选；字段业务含义和原题完整性仍由当前 Agent 核对。真正有多个会改变答案的合法业务选项才调用原生 HIL；目录缺项、结构变化、物理编码冲突或工具故障应说明阻断。`enforce` 执行层以原生 Run 事件记录相同错误字段与期望/实际；同类三次无新证据拒绝后停止新的正式查询，连续六次不同拒绝也停止。只有新的目录/实体/探查事实、成功取数或原生 HIL 回答重置预算；改 SQL 文字、换 Playbook、重提相同目录或改输出路径不算进展。`legacy` 不启用业务计划 Gate 与该修复限额，但仍执行独立 SQL 安全策略。

**HIL 选项本身也要有证据。** 组织层级未知时，只能选择已证实的单一组织或分别列示；不能提供“可能重叠的组织相加”或“某编码已包含下属单位”的未证实选项。模糊的改善幅度必须澄清指标名、单位和比较基期，不能只问基地范围。用户请求“官方均价”时，先说明当前目录能否证明官方发布；不能把所有日期、城市、规格混合平均当作官方指标选项。跨期价格不可比时，分别核查用户给出的两个目标期，不能把一月行情误说成三月行情缺失。

**结构化拒绝与新增表。** Gate 的 error.diagnostic 返回 error_domain、field、expected、actual。先判断错在 SQL 还是合同；依据新证据重建计划时从原题重新检查必需条件。新增表沿用目录定义与物理 Gate；没有业务语义时标记未证实，不从列名猜口径。

**分编码时间字段。** 同一时间字段可按目录中 selector={field,value,period_length?} 的当前定义选编码。time_bindings 携带同一 selector，物理 SQL 每个扫描都以参数化等值条件落实；有 period_length 时还须以 LENGTH(时间字段)=%s 限定。缺选择器或匹配定义不能绕过正式取数。compose-plan 支持 --time-selector-field、--time-selector-value、--time-period-length。

**业务筛选的物理证明。** 用户明确指定的合同类别、币种、数据类型等源字段筛选，可在 typed intent 中声明 filters 数组，每项为 source_id、field、value；compose-plan 会复制到 filter_bindings。执行器检查每个物理扫描 WHERE 中相同字段的参数化等值条件。物理匹配不能证明字段业务含义；语义仍要来自目录或用户明确条件。

**正向问题拿到足够数据就交付。** 完整计划的正式查询已经返回所问实体、项目和期间的数值时，先用这些结果核对比较方向与计算，再直接提交最终答案；不要为了附加说明反复重查、改写计划文件或补不相关的探查。已唯一查证的单一组织编码且用户没有要求合并时，不发起组织范围 HIL。若后续审查指出明确缺口，只补该缺口；不要把已核验的数值重新取一遍。

用户只比较不相邻的两个月时，可把两月之间的连续期间作为同一个 typed `time_range` 和 `time_bindings`，以完全一致的半开范围执行正式查询，最终只列用户所问月份；不要在计划声明连续区间却用 SQL 的两个离散区间取数。不能为了通过校验删除本题必要的期间、指标或业务意图。

读取当前 `get-query-context` 后，按 [五类 Playbook](references/question-playbooks.md) 对每个候选逐一检查必要槽位、反例和 blocking。CLI 实际动作包括 `decide`、`probe`、`compose-plan`、`execute`，不要使用其他动作名。调用 `scripts/data_client.py decide --scenario-id group --request-json <typed-intent> --output <文件>` 保存裁决回执。`pattern` 必须是 Playbook ID，例如逐月趋势用 `period_comparison`；`time_range` 必须恰好是 ISO 日期 `{"start":"2025-01-01","end":"2025-04-01"}`，不传 `grain`、`decision`、`no_aggregation_across_months` 等未知键。分数仅帮助排列阅读顺序。`proceed` 后将**同一个原始 typed 输入**作为 `business_intent` 放进唯一的 `nl2sql.query-plan/v1`，不要放裁决回执；`clarify` 用原生 `request_human_loop` 获取会改变结果的业务选择，恢复后重新取当前目录并裁决；`reject` 报告阻断原因。裁决回执与模型提供的 `selection_evidence` 都不是可防伪的 HIL 凭据，执行前仍需复核。完整形状见 [访问契约](references/input-contract.md)。

分类题使用 `{"pattern":"category_distribution","dimension_fields":["<当前表的分类字段>"]}`，不是 `dimension_distribution` 或 `dimensions`；分类项目可以没有正式 metric，仍需核对当前字段和项目值。单个已解析实体使用 `entity_bindings`，不要为它伪造 `scopes`；`scopes` 仅用于真正比较两个独立范围。`decide` 返回 `business_intent_invalid` 时先按输入契约修正字段，不把输入错误说成 Gateway 故障或请求用户选择业务口径。

物理事实探查只使用 `scripts/data_client.py probe`：当前期间最大值或某字段前 50 个有序不同值。传目的、已选源和字段，查询由脚本生成并经同一只读 Gateway 与审计；结果不定义业务口径，也不证明值域完整。不能省略正式取数的 `query_plan` 来探查。自然时间只解析一次为 ISO `[start,end)`，再按当前 `period_formats` 编码 SQL 参数；SQL predicate 不再交给自然时间解析。

如果用户指定的目标期间严格晚于该来源的全表最大期间，`probe` 的 `latest-period` 可证明该来源没有目标期间记录；如实说明当前来源的最大期间，不报 0、不推算。若目标期间不晚于最大期间，或需要分组织判断空值，则仍须带完整计划正式查询，不能用全表最大期间代替实体级取数。

`MAX(period)` 只给上界，不能据此断言更早的某年“有数据”。完整计划的正式查询若已精确限定用户要求的源、实体、指标和期间，成功返回 0 行，就报告该限定范围无记录；不要因空集要求用户改指标、改主体或换期间。跨源比例或合并前，先逐源核查目标期间覆盖：若目标区间晚于某来源最大期间，直接说明该来源缺数据、该比较不可计算，不能先发起与结论无关的币种或指标 HIL。较早区间仍须正式查询核实，不能从最大值推断覆盖。

只要某必要来源在用户指定期间无记录，就直接回答原问题不可计算并停止；不要主动提出未经核验的替代年份，更不能声称另一来源在替代年份有数据。用户随后明确要求改期间时，再分别核对每个来源的实际覆盖。无记录是缺分母，不是数值分母 0。

此类最终回答只需说明缺记录的来源、已验证的期间上界、目标期间和不可计算的派生量。不要为不可计算的比较额外给出另一来源的金额、声称月度与累计可互证、或建议一个未经双源验证的替代期间；逐句检查时间先后关系，例如 2024 年末不可能晚于 2026 年中。

`enforce` 正式取数先从 `get-query-context.plan_seed` 建立计划，原样复制 `resolve-entity.query_plan.entity_bindings` 的完整数组，尤其保留 `entity` 和 `lookup`。补充期间与筛选，放入同一 typed `business_intent`，再提交参数化 SQL。`legacy` 可省略计划；即使提交，结果也标为未验证，Agent 仍须按用户原题核对答案。模式只有 `legacy` 与 `enforce`。

单源、单连续期间的普通指标问题优先用包内确定性 `compose-plan` 复制完整回执：`python3 scripts/data_client.py compose-plan --context @workspace/context.json --decision @workspace/decision.json --entity-result @workspace/entity.json --time-field ny --output @workspace/plan.json`。文件名按本次实际输出替换；无实体时省略 `--entity-result`，无期间时省略 `--time-field`。裁决须为 `proceed`；命令直接保留 `plan_seed`、完整实体 lookup、原始 typed 意图并按字段生成 ISO 时间绑定，不调用模型、数据库或执行 SQL。ratio、双 scope 和不连续期间继续按访问契约显式构建绑定。随后 `execute --query-plan @workspace/plan.json`。不得为通过 Gate 在计划里裁剪实体定义或 lookup。

Ratio 与双 scope 仅采用 [访问契约](references/input-contract.md) 声明的可验证 SQL 形态。共享主体的 company/headquarters 分别查证源、编码和期间，允许重叠，不合并编码。分类项目按维度/项目处理，不动态创建组织 Entity Role。`source_signatures` 只证明结构；没有带来源的同一快照/水位时，不把跨源结果合并为同一时点事实。查看 `verified_claims` 和 `agent_review_required`，物理条件通过仍需核对公式、单位、业务含义与最终答案。

比例先明确 `ratio.kind`：`part_to_whole` 要求分子项目包含于分母全集；`a_over_b` 支持两个互不包含的项目。两者都要求同源、同度量字段、同粒度与零分母 `NULLIF`；SQL 可采用已证明等价的 分子用 `ELSE 0`，分母可用 `ELSE 0/NULL` 或缺省 ELSE。其他表达式不得冒充已验证；若源、组织、期间或单位不一致，应说明不可比或澄清业务选择。

实体查证若在所选源唯一解析出编码，就按该编码回答；用户未要求总部或子公司时，不因相似名称或编码前缀再发起范围 HIL，更不能提出无证据的相加选项。即使用户给出组织编码清单，也还需证明口径互斥才能加总。全表 `probe distinct-values` 是未加本题筛选的有限观察，不足以宣称本题有多个内部报表口径；遇到“管理合并”等限定，先用完整计划的正式查询选出本题公司、项目、期间、币种、数据类型及内部口径描述，再判断是否仍有多个候选。

用户要求“集团人数”但目录缺组织层级时，HIL 只可询问可直接回答的单项或分别列示；“由用户给编码清单后求和”仍缺互斥/不重叠证据，不能作为可直接执行的选项。若用户要自定义合计，先要求组织成员和加总口径的可核验定义，确认后再检查计划与物理条件。

这类 HIL 的可执行选项应限于“只取已查证的单一组织编码”和“分别列示已查证组织，不合计”。若用户坚持要集团合计，用自由文本请求现行组织层级定义、成员范围与去重/互斥规则；不要把“全部月报组织记录求和”列为选项，即使旁边附有不等于集团人数的警告也不合适。

用户要求价格的名称、单位、频度时，在相应指标信息表逐项核对（例如 `unit_name`、`frequency_name`），必要时用 `get-columns` 补取字段并按目录允许的关系联查；不能因时序数值表没有单位列就说整个来源无单位。只拿到历史最后观测时，标明观测日期，不称为“现在价格”。完成率、差额等派生数值只用明确的公式和实际数值计算；不要附加未经核对的替代公式或等价关系。

分类结果的每一行都以来源字段值作键，例如 `report_item_des` 对应 `headcount`；写最终表格前逐行核对“类别 → 数值”映射，不凭排序位置填值，也不把中级与初级、月发生与累计等相邻标签交换。SQL 和计划通过仍不能替代这一步答案核对。

多个候选来源有近似名称时，先核对本题的实体、指标和目标期间是否真的在各来源成立；缺实体或缺目标期间的候选不列为同等可选项。若唯一来源与用户原话精确匹配，就使用该来源；只有仍存在会改变结果的多个有效口径时才发起 HIL。HIL 选项只能提供已核实存在且可执行的选择，单选的互斥组合将 `minSelections/maxSelections` 都设为 1。

目录摘要称字段或项目不存在时，先用本源 `get-columns` 和现有目录核实真实字段，不能仅凭摘要发起 HIL。若日期字段的当前 `period_formats` 声明与该表已查到的实际值编码冲突，保留冲突并如实说明计划校验阻断；用户已明确指定日期和日度时，不让用户重新选择月度口径，也不删时间绑定来取数。查询观测值并附其同编码的指标名称、单位时，分别标注时序值和指标信息来源即可；只有用户要求同一快照的联合事实、且缺少可核验证据时才澄清或拒绝。

发出 HIL 前检查表单是否可由用户直接作答。选择项必须是已从当前目录查证的真实候选，不得使用“占位”“待核实后替换”等选项；如果候选太多或尚未列全，用原生表单的自由文本字段询问规格、地区、价格类型等必要条件，并说明已知的数据日期限制。不要让用户选择一个不存在或尚未证实有目标期间数据的来源。

模型 SQL/绑定错误在同一已确认口径下依据具体诊断逐项修正；每次修正要改变导致拒绝的条件，并验证是否推进。相同诊断反复出现且没有新证据时停止；目录或口径变化重新裁决。应用准入 429、模型上游 429 和查询失败分别报告阶段与请求 ID；只对确认未执行 SQL 的暂时性限流做一次幂等重试。空集与故障分开报告。

## 回复规则

- 默认先给业务结论，详略随问题复杂度决定。单值问数通常一两句话，包含数值、单位、日期和必要的主体限定；来源用简短业务名称即可。用户要求明细、趋势或对比时再展开表格或图表。
- 只解释会改变答案或影响解读的口径、歧义和限制，例如价格类型不同、多个主体数值不同、缺失目标日期或采用替代日期。多项指标数值相同不能据此认定口径相同或互相验证；保留有业务意义的区别即可。
- 查询过程与核对留在内部，不默认附加“口径说明”“数据可得性”“证据链”“局限”等固定章节，也不罗列排除的候选、无关覆盖期或通用免责声明。确有影响结论的问题时，在答案旁简短说明。
- `query_id`、`catalog_revision`、SQL、物理表名、结果文件路径及工具回执属于内部追溯信息；用户要求 SQL、来源明细、审计或排障时再按所需范围提供。用户要求的数据文件或报告仍正常交付。

## 证据与执行边界

- 用户问题决定目标，元数据和查询结果约束事实。目录中的方法建议不能自行增加用户未要求的业务条件。
- 字段值域与本次 DISTINCT 观测范围不同；组织别名、层级与合并口径需要证据，不猜等价、不混加报表项目或层级。
- 工具结果通过 Runtime 正式 Result 保留；跨步骤消费继承的 ResultRef 时，先对每个继承的 `resultId` 调用一次无 pointer、offset、limit 的 `read_result`，满足原生依赖消费约束，再按需读局部内容；不要靠步骤摘要重建证据。完整响应或完整小数据集已内联时直接使用；其他情况按回执指针读取完整文件或确定性计算，不因读取预览省略而重复查询。只看部分排序记录不能证明对象不存在。
- `dataset.row_count` 必须与完整 `rows` 一致；超过结果上限时明确失败，不交付未声明的部分成功。查询回执只证明执行事实，不能证明业务回答正确。
- `connections.json` 只作为脚本配置输入，不加入报告、工具参数或日志。连接或依赖不可用时指出具体阻塞，不询问无关项目路径、不改宿主授权、不启动替代服务、不降级直连。
- 本包按场景隔离，不提供用户级认证。连接账号及权限由宿主决定，允许使用 root 等高权限账号，不检查 `SHOW GRANTS`、不要求独立只读账号。业务查询仍只允许访问当前场景授权表的单条 SELECT，拒绝写入、越界读取和危险函数；真实连接或权限不足错误正常报告。TiDB 不支持 `START TRANSACTION READ ONLY`，不启用伪实现的 no-op 开关，使用 SQL 策略、查询超时和结果限制约束执行。HTTP 接口仅监听本机；只有用户明确要求 HTTP 形式时才启动包内服务。数据源业务数据只读，唯一数据库写入是配置目录数据库的查询审计表，不写业务表、不修改配置、不初始化数据库。
