# 从问题到受控 SQL

规划由当前 Agent 完成。元数据、查询与分析按需要穿插；简单问题不必为了满足流程而增加模型轮数。

本 Skill 固定使用 `group`（集团经营分析），开始规划时直接读取 group 目录，不要求用户重复选择场景。只在 group 的授权表及业务定义范围内分析；用户要求其他场景时说明当前范围。实体、指标和口径的歧义确认仍是独立决策。

## 通用语义框架与场景知识

运行时只依赖通用语义结构：来源、字段、实体、指标、期间、值集、关系、证据和缺口。`kind`、`semantic_role`、关系 `predicate`、标签和别名均由目录数据维护，不在 Skill 代码中枚举某个行业的对象名称。集团财务、人力或经营分析的专业知识属于 `terms`、`entities`、`metrics`、`relationships`、字段定义和 Skill 提示中的场景配置；它们必须绑定当前来源，不能被提升为跨场景事实。

字段结构负责存储类型、格式、长度、精度和可空性；语义对象定义负责维护可执行对象与来源字段绑定；`terms` 是人员维护的业务术语真源，包含规范名称、含义、别名和证据，语义图里的 `term` 节点只是它的检索投影，不应在另一处重复编辑；关系负责表达本场景中有证据支持的连接。定义不完整时返回缺口并先做有界探查；仅当查证后仍需用户决定业务含义时才 HIL。探查结果保持 `observed_only`，不能自动改写全局目录。

## 意图与领域绑定

为每个目标确认指标定义与单位、对象范围、时间范围、筛选条件、分组粒度和排序/比较集合。将这些语义绑定到目录中的来源、字段、指标公式和时间规则。记录会改变结果的假设，不能让用户未要求的示例或目录建议变成强制筛选。

先用 `retrieve-knowledge` 获取问题对应的术语定义、指标候选、目标表、命中依据和缺口。此阶段只检索 TiDB 中维护的知识快照；`schema_verification=stored_snapshot_only` 不证明物理字段仍然存在。分数用于安排读取顺序，不能排除低分的必要来源；候选分页必须可扩展，多指标和多来源分别定位，显式关系涉及的表按需补读。未命中正式指标不证明无法回答，先判断是否需要精确搜索、字段探查或澄清。

直接读取来源已经提供的值时，使用术语的 `data_bindings`，不另行发明公式；有多个绑定时依据业务定义显式选择，并用 `term_refs` 带入上下文。需要加工计算时采用正式指标。选择来源及正式指标后，用 `get-query-context` 一次取得必要上下文，传同一 `catalog_revision` 与源绑定的 `metric_refs`。它只刷新选中表的物理字段，按指标公式、项目条件、粒度、实体和期间依赖返回相关字段；需要其他维度时用 `columns` 显式补齐。仍不清楚字段时先 `search-columns`，已知名称时 `get-columns` 批量精确读取。完整业务定义、单位、粒度、来源证据和关系限制必须进入领域计划；仅字段同名不足以证明业务含义。

执行计划优先只传 `context_id` 和本题新增绑定，服务端恢复完整种子及不可变证据，不手写或复制完整 `plan_seed`；存在适用于当前对象、字段或指标的 blocking gap，或缺少本题实际需要的来源、指标、期间语义绑定时不得进入 SQL 执行；实体绑定属于可选证据。仅声明某来源但 `affected_refs` 还指向其他术语/对象的缺口，不阻断无关查询；来源级缺口只在其影响对象被当前计划绑定时生效。正式指标绑定为 `{source_id,metric_id}`；实体绑定来自真实编码查证时才加入，时间绑定表达本题要求的具体区间；用户已给出物理编码或模型仅保留实体过滤时可以不生成 entity_bindings。期间编码未知先探查真实存储值及其时间类型、单位和项目范围，不能让用户选择物理编码格式。字段期间格式保留在 `period_formats`，不能当作时间筛选绑定。没有指定期间的最新月份查询可仅带源签名计划。SQL 执行器会检查知识版本、当前表签名和已有绑定；结构变化时重取受影响上下文，不能删签名或业务约束绕过。具体请求见 [知识检索接口](retrieval-contract.md)。

`table_summaries` 提供用途、一行含义、指标/维度/组织/时间字段及适用范围。检索快照中 `understanding_status=unverified` 的摘要可用于发现候选，不能当作已核验字段或执行业务定义；选源后由实时上下文核对。执行时只使用表标记 `understanding_status=current` 的摘要；`stale` 或 `invalid` 时读取当前结构与定义，`not_prepared` 不表示表不能回答问题。签名只证明结构与定义一致，不证明样本取值、时间覆盖或组织目录永远完整；查看 `provenance`、`evidence_ids` 和局限，必要时做本题所需的最小探查。`grain_status=multiple_rows` 的候选粒度未通过唯一性核验，不能据此认定一行就是一个业务对象；`verified_unique` 也不证明跨期、跨层级可加总。

SQL 前简要确认会影响本题结果的口径：指标及单位、必要筛选、维度与粒度、时间字段及边界、表与关联键。简单问题可直接在规划中表达，不要求额外交付一张“口径卡”。未确认的状态条件不能照抄其他案例。

- **对象身份：** 用户简称与数据库存储的名称未必相同。优先查目录中的别名、实体编码及关系；需要探查时先对用户给定线索查询 DISTINCT 名称与编码，确定候选后再读取相关指标项目，不把所有名称或全部报表行当作身份定位的输入。包含匹配只能发现候选，不能证明所有匹配组织都应该相加。父组织、分支与总部可能重叠，未确认层级时分别呈现。
- **派生或受限对象：** 对象可以由目录中的 `scope_filter` 限定，也可以通过显式关系连接到其他对象。筛选字段、模式、关系谓词和基数都必须来自当前来源的定义与证据；不能把某个场景的对象名称、字段前缀或编码规则写入 Skill，也不能从名称相似自动推断层级或合并关系。
- **指标含义：** 相似项目名不自动等价。先检查值域与指标定义，确认人数、金额、比率及单位。行数、去重实体数、业务报表项目值是不同指标。不得将不同报表项目或不同层级混加。
- **期间：** 按目录编码转换用户日期，区分自然月、财务月、月末快照与累计值。快照通常不跨期相加；同比/环比必须有可比区间。
- **关系与粒度：** 仅使用已确认的关系。先检查主从关系与重复风险，再决定去重或预聚合。独立来源并列比较不要求 JOIN；不得因缺少关系而臆造公共键。

## 将目录定义落实到 SQL

- **指标与术语：** 术语的别名用于解释问题，`meaning` 用于区分概念。采用指标时同时核对 `expression`、`project.field/value`、`grain`、单位、描述和来源证据；报表项目存于行中时保留精确项目条件，不能只选数值字段无条件 SUM。AI 摘要中的 `metric_clues` 只提供候选线索，不等于已核验的正式指标定义；与人工定义或实查结果冲突时先查证，不悄悄覆盖。指标未定义时可按用户目标和已确认字段自行推导，说明真正影响结果的假设。
- **组织与对象：** `entities` 的 `source_id/key_field/name_fields/aliases` 用于定位本表实体。`definition_status=invalid` 的定义不可直接绑定。别名只帮助发现候选，真实编码才是最终等值或 IN 条件；有多个合理候选且不能确定时交由用户选择。不得将组织样本当成完整名录，不能为得到结果将精确范围改成 LIKE。
- **期间：** 字段定义中的 `format/granularity` 是本表存储编码的首选来源（例如字符串日期明确写成 `YYYYMMDD` 或 `YYYY-MM-DD`）；历史 `period_formats` 只作为兼容引用，且必须与字段定义一致。按该定义转换用户期间；结合 `timezone` 和 `time_policies` 处理有影响的日期边界，不把其他表的期间格式复制过来。无效或冲突定义必须重新核对。期间编码一致不证明快照、发生额和累计值可以同样聚合。
- **执行前后核对：** 按本题对照实际 SQL 的项目、实体集合、期间参数和聚合粒度，执行后再对照结果对象与单位。不要把“定义存在”“查询成功”当作口径已经落实的证明；目录不替代数据库执行器的只读和场景授权校验。

### 术语到实体的显式绑定

`retrieve-knowledge` 的 `terms` 保留命中文字、`match_scope=exact|context`、完整 `definition` 与版本绑定的 `definition_ref`。读取 `definition.meaning/aliases/provenance`。同一文字既是正式术语又是另一术语的别名时，正式术语优先；context 仅表示在问题中出现，不能据此确认整句话与该定义等价。先解释 `meaning` 确认本题对象的规范名称；不能看到术语后，仍只把原始简称拼成 `LIKE`。术语命中只证明词面匹配，不证明它指向哪张表，也不自动把自然语言定义转成公司编码。

对目录中已有 `entities` 定义的目标表，执行 `resolve-entity`：提交 `mention`（命中的术语或别名）、`matched_term`（术语名称）、`canonical_name`（由该定义解释出的名称）、`source_id` 与 `entity_id`。脚本保留原始定义，用本表 `name_fields` 对规范名称做参数化精确查询，返回候选名称、真实编码、查证 SQL/参数、`query_id` 和目录版本，并生成 `nl2sql.query-plan/v1`。没有命中完整术语且用户给出规范名时可省略 `matched_term`，即使规范名包含对象别名（例如“安宁基地”包含“基地”），也只按该完整名称做精确查证，不自行扩展简称；若整个输入就是术语或别名，仍需提交 `matched_term`。歧义、否定或非同义的术语含义仍由 Agent 判断，脚本不从自然语言机械猜等价关系。

`resolved` 表示规范名对应唯一编码；`ambiguous` 保留所有候选，`selected_codes` 初始为空。根据用户选择或已核实的业务范围填写编码，并保留 `selection_evidence`（如本 Run 的 HIL 答复引用）；无法确定就询问，不把所有候选自动相加。`unmatched` 不是零业务值：先检查术语理解、实体定义与存储名称，不能回退到任意简称模糊匹配。跨表使用同一对象时按各表实体定义分别查证，不复制另一表编码。

实际取数带上该 `query_plan`；如果存在实体绑定，完整保留 `mention → matched_term.meaning → canonical_name → entity.source_id/key_field → selected_codes → lookup.query_id`。执行器只在存在实体绑定时核对当前目录、候选证据与 SQL AST；没有 entity_bindings 时，SQL 仍可使用参数化实体过滤，执行器不因缺少绑定而阻断。`SELECT` 中出现编码、其他表上的同名字段、名称 `LIKE`、可绕过编码条件的 `OR` 均不算落实。别名和在内层完成编码筛选的 CTE 可核对；仅在外层筛选派生表、只在 JOIN ON/HAVING 中限制编码等不能证明的形态会明确拒绝，应把本表筛选放在其物理查询层，不静默改写 SQL。此项核对只验证实体筛选；同一计划还可核对正式指标的项目条件及期间边界。核对范围以 `verification_scope` 为准，公式、粒度、金额单位及结论仍需 Agent 审核。

未配置 `entities` 的表仍可查询：先结合术语和物理字段小范围核实规范名称与编码，将同样的映射及来源留在领域计划中，并明确尚无自动实体核对回执；不凭空创建“current”定义或伪造解析结果。无具体实体范围的汇总、项目探查无需构造空绑定计划。

## 同一次执行中的查询计划

采用正式指标时用 `metric_bindings: [{source_id, metric_id}]` 引用其 `name`；明确期间时用 `time_bindings: [{source_id, field, start, end}]`，起止为 ISO 日期，右边界不包含。模型附带的期间存储格式或粒度只作为可核对证据，不能替代区间。二者与已有实体证据放在同一个 `nl2sql.query-plan/v1`，可以直接内联到 SQL 请求，不增加固定的“规划→验证”工具轮。具体结构与示例见 [数据访问契约](input-contract.md)。

少量绑定可直接补入请求 JSON，保留原实体证据即可，无需专门生成并运行一个合并计划的脚本。事实步骤可直接复用正式查询与计算 Result，无需额外编写一份事实稿才能交接；确有对已有查询结果的分组、计数、均值或中位数计算时，调用声明的 `compute-result`，输入必须是当前 Run 的结果文件，输出保留输入哈希且有界。跨步骤仍通过 `read_result` 正式消费输入，不能用临时脚本、`python3 -c` 或这些简化替代 Result 绑定与消费。

脚本从当前目录派生指标 `project.field/value` 和期间存储编码，不接受 Agent 另写一份映射。每个物理源的 WHERE 用参数化 `=/IN` 保留恰好所选项目值，以 `>= start AND < end` 保留期间；多个项目同源时按绑定项目全集筛选并正确分组或条件聚合。无法证明的 SQL 形态应调整物理查询层的筛选，不能删除计划绕过。纯探查不必构造空计划；没有正式指标时仍可依据已查证字段生成 SQL，不能伪造 metric_id。

文本或数值时间字段缺字段级 `format/granularity`（且没有一致的兼容 `period_formats`）时，自动期间核对明确返回 `time_definition_missing`；不从描述猜格式、不复制其他表编码、不硬编码某业务表。先用有界值探查确认。回执非空、完整、无 NULL 且编码一致时，可在紧凑计划加 `probe_refs:["<probe_ref>"]`，SQL 保留探查全部精确筛选；执行器会实时重探、派生当前查询范围内的编码，保留 `observed_only`，全局缺口不变。不向 `decision_refs` 填机器证据，也不通过 `resolved_gap_refs` 假称人工确认。截断、混合或未知编码需要继续缩小探查范围，不能直接执行期间查询。月度边界必须按月对齐，快照、月发生额和累计值的可加性仍由 Agent 判断。摘要中结构化粒度证据与旧局限文字冲突时保留冲突并查证，不把任一条文字当成自动覆盖规则。

## SQL 与错误恢复

使用明确的 TiDB/MySQL `database.table` 和字段，参数占位符为 `%s`，参数单独传递；不把参数值拼入 SQL。只查询当前问题必要的数据：实体和项目确定后，单值问数筛选对应期间、实体与项目，不读取整份报表再从中复述其他指标。探查结果须注明探查范围，LIMIT 过的候选列表不能声称完整。`allow_output=false` 的原始字段不直接输出；服务端仍会独立校验。

本入口使用 PyMySQL 的 `%s` 参数数组约定，目录标明 `database_engine=tidb`、`sql_dialect=mysql`。日期示例：`sale_date >= CAST(%s AS date) AND sale_date < CAST(%s AS date)`，对应独立参数 `["2026-06-01", "2026-07-01"]`；不要使用 PostgreSQL 的 `::date`、`ILIKE`、`DATE_TRUNC` 或 `$1/$2`。MySQL 日期截取使用 `DATE_FORMAT`，日期运算使用 `DATE_ADD`/`DATE_SUB`；模糊匹配使用 `LIKE`，需要忽略大小写时按真实排序规则或 `LOWER` 明确处理。`DATE '2026-06-01'` 是 SQL 字面量语法，不能套成 `DATE %s` 或 `DATE $1`。绑定失败不证明日期参数不可用，也不能成为内联用户值的理由。

目录足以支持目标 SQL 时，直接执行有业务目的的查询。`SELECT 1` 没有引用授权表，会按策略拒绝；不以此检查连接，也不机械执行全表 COUNT、MIN/MAX 或不含目标期间的分布。仅在缺失事实会影响口径或结果解释时做最小探查，保留必要过滤条件。

先根据领域计划生成 SQL。策略拒绝时读拒绝原因并修正不合法引用或操作，不绕过限制；执行失败时根据目录、错误代码与 SQL 定位，无法确定就说明失败。空集合和 NULL 不等于 0：先区分筛选未匹配、项目缺失或源数据为空，再决定有依据的探查或澄清。

恢复先看 `error.diagnostic.phase/code`。`query.bind` 下的 `unsupported_parameter_style` 或 `parameter_count_mismatch` 是请求参数错误，按 `%s` 与参数个数修正；业务 SQL 尚未提交。`query.explain`、`query.execute`、`result.fetch` 属于不同执行阶段；有 TiDB/MySQL `vendor_code` 时据此定位，无代码或无原始错误证据时不得断言是参数、字段、VPN 或数据问题。不重复执行同一已知失败组合，不通过删掉业务筛选使查询“成功”。

核对按风险选择：JOIN 可能放大度量时，按实际主从粒度检查去重或预聚合；`COUNT(*)` 和 `COUNT(DISTINCT 订单主键)` 可以不同，不能要求一单只有一条明细。分组合计与独立总量只在口径一致且可加总时比较，不累加比率或重叠实体。日期边界由字段类型、条件与目录口径决定，不能用总行数比例证明。已有结果能确定性核对时直接计算，不固定增加多条核对 SQL。

涉及多条查询时分别保留请求和结果，按依赖顺序执行；无需为了修正单条 SQL 重新执行已成功的查询或整套流程。
