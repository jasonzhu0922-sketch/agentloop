## 新发现：实时与恢复的声明投影不等价

b79ee9ca 第 18、19 步因缺 command 在 prepare 阶段被拒，事件 seq519/539。两个 assistant checkpoint 仍保存了原生 context 声明。

实时 `agent-loop.ts` 的 rejectedProviderToolCalls 分支将这些调用从原生 transcript 排除，相应声明也未进入实时工作集；最终实际记录为 **8 个当前条目、13 次释放**。

`reconstructRecoveryTranscript` 在恢复时主要以参数是否为对象判断 replayable，没有在同一过滤中排除 outcome.failurePhase=prepare；它重新构造这两组调用和结果，其上的声明被再次消费。对同一批原事件离线重建得到 **10 个当前条目、14 次释放**，额外条目为 period-probe / probe-period-2026h1。只在内存中过滤这两组 prepare-rejected 原生调用后，立即恢复为 **8 / 13**，与实时记录一致。

这个实验是同一事件源的反例与定位，不是已完成生产修复，也没有实际重启或重复副作用。它说明语义声明生命周期仍与 Provider 消息过滤耦合。修复应统一实时与恢复对同一正式声明的解释，再独立处理原生协议编码；不能通过另建一套状态、简单删除有效声明或放宽授权“修平”差异。已知效果与未知效果仍应由 Action ledger 决定。

## 后续优化优先级

1. **恢复等价性优先。** 用上述真实模式增加包含 prepare rejection、context 元数据、重启和未执行效果的回归，统一 live/recovery 的声明适用规则与 Provider 过滤边界。
2. **再改善实际承接可靠性。** 从同一正式证据及请求基准派生生命周期，拒绝后给准确可修复的引用/版本信息，避免错误 id、拒绝的前序条目和新旧 id 混用形成连续失败。省略 absorbs 仍不能自动推定正文已充分承接。
3. **评估解决证据选择和充分性。** 同一有效工作集按目标生成评估证据；保留缺口及可读原文入口，必要时读取。领域来源、主体和口径由所属 Skill 提供与核对，工具成功和 verified 不可替代完整目标证据。
4. **以同题成功且正确的业务结果做真实对照。** 固定包、配置、任务及尽可能一致的来源，比较累计 tokens、输出、读取、调用、耗时、业务完整性与恢复等价性。不能拿失败基线、不同指标或只比较末轮输入取得“优化成功”。
