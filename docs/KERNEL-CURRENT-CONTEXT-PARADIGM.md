# 当前上下文驱动的运行范式

后续契约已收敛为唯一原生参数入口；本页保留当时实现与测量。最新变更、验证及未通过边界见 [内容生命周期优化](KERNEL-CONTEXT-LIFECYCLE-20261125.md)。

状态：2026-11-25 顶层设计基线。后续已实施语义/Provider 解耦、提交后派生及独立评估选材；实现、真实模型对照与未验收边界见 [本轮实现记录](KERNEL-COMMITTED-CONTEXT-IMPLEMENTATION-20261125.md)。本设计中的全部迁移目标并不因此自动视为验收完成。

## 先纠正问题定义

目标不是使历史消息变短，而是让一次模型决策的输入，由当前任务所需内容生成。两者的根本差别是：

```text
当前实现：历史消息 → 尝试提取当前状态 → 声明吸收历史 → 剩余消息继续输入
目标实现：正式状态与证据 → 当前决策依据 → 阶段所需实际内容 → Provider 编码
```

完整历史一直存在；常驻模型输入不是历史的默认副本。工作集是权威记录的投影，不能成为新的授权来源或事实数据库。

前两轮实现修复了真实读取与编码问题，但整体仍属于第一条链。通过增加 kind 容错、revision 修复和证据去重，无法把这条链自动变成第二条链。

## 当前源码中的三个反向依赖

1. `deriveDecisionWorkingSet` 先从 `ModelMessage[]` 找完整原生交换，再处理语义声明；没有形成原生交换的正式声明不会参与实时状态。语义层因此依赖消息编码层。
2. `ContextAssembler.projectToolEvidence` 用执行阶段 absorbed/pruned 消息结果选择评估证据；`run-service` 再基于这些调用生成 evidenceTimeline。评估证据选择因此依赖执行消息的保留情况。
3. `recovery-transcript` 重建 Provider 可重放消息后，恢复规划才从这些消息重建 working set。恢复语义因此依赖另一套 Provider 消息过滤。

b79ee9ca 的 prepare-rejected 声明使实时/恢复条目变成 8/10，正是第 1、3 个依赖不一致的反例。评估 12 万以上实报输入 tokens，说明第 2 个依赖仍在携带大量执行历史。问题不是某个工具字段太长，而是输入生成方向反了。

另一个边界：`CurrentDecisionView` 当前已有 Canonical 目标、产物和 gap，但其 toolFacts digest 仍包含全部传入工具证据；`eventWatermark` 又是 WorkProduct observation 计数，不是完整正式事件水位。新范式需要区分审计水位、完整证据清单和当前决策内容摘要，不能用其中一个冒充另外两个。

## 一次决策的统一基础

扩展既有 `CurrentDecisionView` 的输入和投影职责，在内部形成以下逻辑决策依据；这不是要求新增同名持久化协议、四张表或第二个 Canonical 状态。

| 组成 | 权威来源 | 核心约束 |
| --- | --- | --- |
| 当前任务契约 | Canonical intent、原始用户修订、HIL/decision ledger、已准入目标 | 原文、优先级、作用范围与验收语义保真；模型摘要不能授权 |
| 当前有效观察与模型判断 | 已提交 Result/事件、WorkProduct 观察、带依据的模型声明 | 事实内容、模型解释、推断、未知和冲突分别保留；声明不能自授验证状态 |
| 当前成果及依赖 | WorkProduct 版本、检查绑定、已接受 Result、目标与候选绑定 | 存在、当前版本、验证、用途和最终交付分别判断；文件仍存在不等于本轮必须读取 |
| 未解决义务与效果边界 | Canonical open gaps、未兑现选择/承诺、Action 状态与恢复决定 | 旧问题有适用性；未知效果不能因正文离开输入而消失 |
| 本轮必要正文与历史入口 | 原 Result、ContentReference、已有 pointer/window 与读取覆盖 | 精确身份、版本、范围、hash、授权；必要正文实际装入，引用不能充数 |

同一正式记录、水位、任务修订和投影版本，应生成等价的语义依据。live、HIL 恢复、取消后恢复和新进程重建共用同一解释规则。投影缓存可增量更新、可丢弃、可重建，不接受绕过正式事件的独立事实写入。

不把所有仍存在的文件自动选作当前成果，也不按名称猜辅助产物。未经用途判断的新产物保持“未分类”并显式呈现；只有正式目标绑定或带来源的语义选择，才能使其进入候选、输入、实验等角色。未分类不是已无关，历史索引也不是当前必要内容。

## 三种生命周期必须独立

### 证据与内容

内核自动记录新 Result、来源、精确内容、作用域、版本和已提交状态。模型或 Skill 判断结论、相关性、冲突与用途；这个判断在正常决策中提出，内核校验证据、请求基准和权限。

正文不再以“所属原生交换是否被模型手工列入 absorbs”作为最终保留原因。需要表达的是它与当前事实、成果、问题及决策的关系：当前需要、等待处理、被显式替代、当前不适用但可追溯。语义相关性不能由内核按关键词推断。

删除正文之前必须有可核查的承接或处置依据、必要内容的物化，以及准确历史入口。模型没有作出足够判断时保留未处理缺口，不能把“模型看过一次”解释成“必需信息已经保存”，也不能把未选择内容默认为无用。旧 absorbs 只能作为兼容输入，经相同规则解释；它不再统辖三个生命周期。

### 行动效果

Action/Result ledger 继续决定已发生、未发生、失败与效果未知，以及 replayPolicy。语义条目 resolved 不改变它们。

效果未知与正文永久常驻不是同一个概念。不过，在没有完整效果边界、可追溯证据与可验证恢复保护时，不能仅凭短状态就释放相关正文。先保留现有安全行为，再证明哪部分内容可以退出；绝不能通过换一个 ToolCall id 绕过效果未知的恢复边界。

### Provider continuation

adapter 决定工具配对、reasoning/加密 continuation 及服务端 continuation 所需内容。它消费语义依据及必要的原生延续，不生产任务事实。

必须保留的协议内容可能继续增长。测量要将它与“未承接而暂时仍用原生消息承载的普通历史”分开；当前 nativeProtocol 字符数不能直接被解释为 Provider 强制保留量。

## 更新契约：模型负责语义，内核负责机械工作

一轮正常行动的路径应为：

```text
装配已提交的当前依据和必要内容
  → 正常模型调用：选择行动，必要时同时提出语义变化
  → 校验提议及行动权限，按既有规则执行
  → 持久化调用、Action、Result 与事件
  → 从已提交记录增量更新当前依据
  → 生成下一阶段/下一轮所需输入
```

模型判断“这个结果说明什么”“哪个旧判断不再适用”“哪份成果作为候选”。内核处理稳定身份、请求时版本、来源绑定、内容覆盖、失效关系、历史定位和 Provider 编码。不能要求模型反复手抄一组长调用 ID，才能完成本可机械派生的生命周期工作。

同时，内核不能自动把某次结果吸收、关闭问题或推断两份研究结论等价。相关性判断和引用选择不清楚时要拒绝/显式报告；可以把当前请求中已确定的身份和版本绑定到提议，不能借此补充未提出的事实或授权。

语义提议与业务行动是否通过 prepare 是两个判断。建议规则是：来自正式完整 assistant checkpoint、且引用请求可见的前序证据并通过校验的提议，不因同回合业务参数 prepare 失败而丢失；业务行动仍明确未执行。流中没有最终完整 checkpoint 的半截提议不能被当作已接受声明。live 与 recovery 必须共用这个规则，不能通过“恢复时多删两条消息”代替统一语义。

## 内容装配不是再做一次模型选材

输入选择从任务目标、当前阶段、当前成果、未解决问题、显式语义依赖和未处理观察出发，沿现有身份关系取得必要证据。使用这些已经建立的关系生成投影，不在每次行动前调用另一个模型来搜索、排序或摘要历史。

必要正文已经在授权 Result 中、且选取位置明确时，由内核直接物化到本轮输入，保留原 pointer/window、内容 hash 和范围。相同内容/窗口共用一份；必要范围扩大时合并覆盖，不能把多个重复读取永久追加。

未知的读取需求仍允许模型按需 read_result；新增读取结果进入原正式证据体系。若选择关系本身不完整，就显式给出缺口与读取入口，不能假装只保留几条短摘要已经足够。

## 四阶段共用依据，各自选择内容

| 阶段 | 主要内容 | 不应继承的默认行为 |
| --- | --- | --- |
| 规划 | 精确任务契约、已有有效成果、依赖与缺口 | 重新复制每次历史尝试以理解当前目标 |
| 执行 | 当前行动依赖的实际内容、当前产物/问题、授权与能力 | 把全部完成交换当作默认输入 |
| 恢复 | 同一当前依据、失败边界、Action 效果、尚未确定事项、可复用证据 | 先重建 Provider messages，再把它当成语义真源 |
| 评估 | 用户目标、候选、有效成果、必要来源、未解决问题 | 直接把执行阶段尚未释放的 transcript 当作评估证据集 |

评估需明确区分“观察到成功操作”和“证据足以覆盖用户目标”。b79ee9ca 的问题是主体与层级未证明，却因金额一致、时间正确和工具 verified 被接受；修复要让目标范围对应的未验证前提保留到评估，而非在内核加入公司字段或 SQL 特判。

创作、文档与编码的验证需求不同，不得机械规定所有结论必须有工具调用引用。需要外部证据的要求、模型判断和可由程序验证的版本/完整性应分别处理；原 Plan Admission、授权、HIL、产物验收和终态提交继续掌握各自权限。

## 模型轮次是设计约束

采用新范式可能因错误选材、承接失败或只给引用而增加轮次，这个风险不能靠“少一次 summary”承诺消除。设计应排除以下机械开销：

- 没有每轮独立的状态整理模型、选材模型或状态审核模型。
- 没有先请求“整理状态”才能执行业务行动的强制往返，也没有每轮必调的空转工具。
- 有语义变化时与正常决策/行动同回合提出；无变化不重写完整当前状态。
- 已知必要内容从授权存储直接物化，避免“先看引用 → 再发读取 → 再决策”的可避免往返。
- 评估沿用原阶段；只有实际存在新的必要证据需求才补读。状态解释不产生新的权限或二次 HIL。

具体响应传输应复用并演进已有上下文声明协议，由 adapter 处理模型支持差异；不在本设计阶段承诺所有 Provider 能共享一份跨工具 schema。当前每个工具重复声明 schema 的固定输入开销，以及模型写状态的输出开销，都必须实测，不能藏进“系统固定成本”不比较。

理想的正常回合仍是一次模型调用完成一次业务决策。真实模型可能自主多读、重试或改变动作，所以验收必须观察总调用，不能只证明 reducer 是纯函数就声称轮次不会增加。

两个不同的“60%”必须分开：

1. **历史步骤从 100 增至 160，必要工作集稳定：** 后续每轮输入应基本稳定；总调用和累计 tokens 随真正新增工作增长约 60% 本身并不异常。
2. **相同任务开启优化后成本增加约 60%：** 必须核查是否增加了状态输出、补读、失败修复、评估或模型调用；不因末轮输入更短就接受这项回归。

023fd241 比同题 bef6367b 多 2 次调用、输入 +20.1%、耗时 +24.1%，本身已经是必须保留的失败验收样本。不能挑净利润从失败变成功的较短链路覆盖它。

## 从现有实现迁移

| 次序 | 改动边界 | 必须先证明什么 |
| --- | --- | --- |
| 1 | 从既有已提交事件/Result 派生语义依据；解开 decision-working-set 对 ModelMessage 完整批次的依赖 | 同水位 live/recovery/HIL/取消重建等价；prepare 拒绝与半截输出规则一致；没有新增模型调用 |
| 2 | 将证据必要内容、成果版本、未处理观察及声明处置纳入既有 CurrentDecisionView 投影 | 当前内容真实存在且可追溯，版本失效正确，冲突/未知/承诺不丢，未完整时明确报告 |
| 3 | ContextAssembler 从当前依据生成输入，Provider 编码独立；原消息只服务必须的 continuation | 工具配对、reasoning 与效果恢复正确；历史体积不再决定模型常驻输入 |
| 4 | run-service/assessor 按相同依据生成评估输入，替换基于 projectedToolEvidence 的选择来源 | 业务目标证据充分性不弱化，必要原文可直接读或按需读，不能只对 timeline 做再次压缩 |
| 5 | 固定包/模型配置与任务的离线、模拟及隔离真实对照 | 业务完整性、恢复正确性、累计输入/输出/cache、模型调用、历史读取、耗时一起验收 |

所有阶段保留正式历史与原权限。切换前可在相同记录上做不发模型请求、不执行行动的双投影核对；不要为双投影再跑一遍副作用。只有最终选定路径生成真实请求，不以双跑模型证明一致性。

增量投影只处理已提交事件；使用既有事件水位与 checkpoint 基础验证缓存，重启可从原记录重建。不能把“模型输入不随历史增长”与“每轮仍全量扫描历史的 CPU/IO 开销”混为一谈。新设计也应测量后端派生开销，避免只是把线性成本移到装配器。

## 验收重点

- 多领域保真：代码版本/旧错误、研究来源与分歧、分析的范围与计算依据、文档的替代/删除/重建与最终交付。
- 相同有效工作集下增加 60% 已解决历史，检查每轮输入及装配开销；再检查同题正常任务是否产生额外状态回合、读取和状态输出。
- 必须查旧版本才能行动的任务实际读取到必要正文；同值读取不会以多份副本常驻。
- b79ee9ca 的 prepare rejection 反例必须使实时与恢复语义一致，不能靠移除证据取得表面相等。
- 工具成功、事实解释、成果有效、目标证据充分与任务完成分别验收；必要时留作未验证，而非凭较短输入通过。
- Provider continuation 与未知效果可造成必要增长，必须有明确保留原因；不能为了满足性能表强行释放。
