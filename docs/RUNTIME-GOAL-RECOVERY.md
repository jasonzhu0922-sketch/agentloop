# 用户目标、结果验收与恢复契约

本次优化沿用 `CanonicalRunState → Plan/Step → 工具证据 → Assessment/GoalGap → Recovery → TerminalCommitter`。目标、缺口和完成状态继续由同一个 Run 聚合保存；Plan 是可修订的执行策略。

## 1. 保留需求与观察

- Resolver 的结构化决策确定证据需求。不能因为用户说“比较”“分析”就通过关键词把已有输入处理升级成外部资料研究。已有 Result、原生文件转换与 `refresh_sources` 保持各自的输入语义。
- 阻塞性结果条件携带 `basis`，包含原始 intent ID、关联 target IDs、原文引用及推导理由。准入检查身份、引用和目标关系；前置步骤可以引用依赖它的后续交付目标，但不取得目标所有权。
- 明确标为 `execution_method` 的条件不能成为阻塞性用户义务。引用原文并不证明推导正确；Assessor 仍需检查必要条件是否扩大了用户要求。
- 当前有界 `computer_read_file` 正文和 ranges 正文与 Result 读取窗口一样保留。上下文投影只改变模型视图，不能让刚读到的内容只剩路径和哈希。

## 2. 分开执行检查与结果判断

`model_judged` 选择评估方法，不自动要求网页、书面引用或某种来源。`result_judged` 评估原始用户要求；文件类目标也包含 `requested_goal`，不能凭文件回执通过内容验收。

工具观察只能证明实际检查过的属性。文件存在、非空、可解码、尺寸正确不能证明未观察的内容质量。Assessor 可以把缺少支持的内容属性保留为 unverified，也可以用 `contractIssue` 指出计划增添了无依据的要求；后者进入 Plan 修订，不能静默豁免已准入条件。

`FailedBoundary.unmetCriteria` 保存具体条件、target、状态、理由和证据引用，直接进入已有 `CanonicalGoalGap`。`missingEvidenceKinds` 只表示执行证据种类；目标 ID 和任意业务条件文本不再冒充证据种类。

## 3. 收敛与 Recovery

候选拒绝缓存绑定“当前决策依据 + 输出 + 交付候选”。同证据上的改正答案会重新验收；完全相同的重复候选复用拒绝结果。局部候选预算耗尽进入既有 Recovery，不直接等同于全局失败。

Recovery 读取同一个 canonical state/Gap、已尝试策略、授权能力目录及已有证据。修订后的多个前置/交付叶子共享原 Gap；单个前置步骤通过不会关闭结果缺口。预算按策略修订次数累计，换 Step ID 不重置；当前上限为每个 Gap 两次自动修订。

Plan 修订与 canonical 修订在同一个事务内提交。此前已提交的工具证据可在修订范围内继续使用。未知外部作用仍遵守既有恢复安全边界。无效 Recovery 响应会收束为停止 Outcome，不留下仍在运行的 Run，也不生成交付收据。

## 4. 阶段产物与正式交付

同一产物投影三个独立状态：

| 状态 | 依据 |
| --- | --- |
| `verification.file` | 当前文件 SHA-256/bytes 与真实文件检查回执一致 |
| `verification.result` | 当前目标绑定、已接受 claim 的版本/哈希/大小一致，且所属步骤已通过 |
| `verification.delivery` | 上述结果成立，且 canonical terminal 已完成 |

只有最后一种状态可以显示为正式交付。未通过的文件仍可预览、下载，并显示结果缺口与当前版本检查的 caveats。覆写文件不会继承旧版验收；下载时也会校验已观察的哈希。Router 持久化同一份只读投影，Web 根据该状态显示“阶段产物”“文件检查通过，结果尚未验收”或“已交付”。

## 6. 统一当前决策与恢复入口

执行循环在每个模型决策和候选评估边界读取最新提交的 `CanonicalRunState`。`currentDecisionContext` 是读取回调，不保存启动时的状态引用；Plan 身份由 canonical state 提供。当前决策视图的 `identity.canonicalState.revision` 标明实际读取的版本。

`currentGap.assessmentGaps` 投影当前 Step 或其修复范围内仍未解决的 canonical Gap，保留具体验收条件、理由、证据引用、修复方向及累计次数。`currentGap.receipts` 只表示工具回执缺口，`evidence.receiptNextAction` 只表示回执层的准备状态。来源摘要回执成立，不会关闭所问事实的评估缺口；新证据提交后仍需 Assessment 接受对应结果。初始交付目标尚未完成不等同于已经发生评估失败，其他 Step 和已解决 Gap 不进入当前评估缺口。

当前 `nextAction` 和提示投影以这些 canonical Gap 为依据，区分补充观察、修正答案、修订计划、请求输入与停止。缺少观察时保留已授权执行工具，不因为回执齐全进入仅候选收敛；已有观察足够时允许直接修正解释或答案。提示不再同时催促“立即返回替代答案”和“继续补证”。修复方向不扩大或缩减 Run 的工具授权，不指定领域来源或具体工具。

普通执行、人工输入恢复和计划修订后执行，统一通过 `repairFailedExecution` 把可修复的评估失败交回同一个 canonical Gap。局部候选尝试耗尽不能由恢复入口直接提交失败；原人工输入恢复 Action 先收束，后续修订继续沿原 Gap 预算。正式交付仍由 Assessment 与 TerminalCommitter 决定。`step_execution.policy_applied.currentDecision` 保存决策版本、视图身份、方向和 Gap ID，作为该轮只读审计快照。

回归覆盖回执齐全但事实未核实、修复范围继承、同证据答案修正，以及普通执行和人工恢复后局部耗尽再修订、补证、验收与交付。完整单元测试 170 项、内核测试 198 项及包构建通过；额外执行循环用例的 5 项失败已在本次修改前的隔离副本中同样复现。以上不代表正在运行的服务已重启或新真实 Run 已验收。

## 7. 恢复输入、候选就绪与局部修复（2026-11-14）

### 正式继承已提交结果

恢复规划只从 Runtime 提供的 `availableResults` 目录选择 `inputResultRefs`；目录包含 Result 身份、生产者和有界摘要，不把摘要当成原始结果内容。Admission 校验选中的引用，将其保存到现有 `StepExecutionBinding`。模型不能凭空授予读取权限；读取仍核对 Run、Plan、步骤绑定、账号和持久化生产者记录。

显式输入与依赖步骤的已发布 Result 统一投影成步骤的 Result bindings。执行、候选评估与结果发布使用同一组绑定：步骤必须通过 `read_result` 消费输入，后续发布的 Result 在 `inputs` 中保留原始引用。原步骤退役或未通过答案验收，不会抹掉其已成功提交的工具 Result；引用继承也不把这些工具结果升级成已验收答案。现有 Action、Plan 和 Result 协议继续承担存储与授权，不增设结果副本或第二套状态机。

### 统一候选就绪判断

`CurrentDecisionView.candidateReadiness` 从当前绑定、工具证据、待执行计算和 canonical Gap 派生，统一候选收敛与自动评估入口。未读取输入、缺少工具证据、计算尚未执行或仍需恢复决策时，不进入候选评估。`readyForAssessment` 只表示可以交给 Assessment；开放 GoalGap、目标验收和 TerminalCommitter 仍各自依据原有权威记录运行。

通用来源 receipt 就绪不再自动触发 `current_step_evidence_complete` 收尾；物理产物验收同样不自动请求收尾；Agent 明确提交候选与正常执行预算边界仍有效。来源支撑的事实采集与最终答复都由 Agent 在各自职责内综合来源观察，不把提供方的一段渲染直接当作完整事实成果；这不要求固定步骤数或固定工具调用数。候选准备提示须与实际暴露的工具目录一致，允许针对性补齐未回答的事实。

预算末轮若成功执行正式标记为只读的工具，沿用现有的一次 `completion_observation_consumed` 续步来消费返回值并提交候选；不会因为连续读取而反复续步。文件/JSON 读取仍正常发布工具 Result，`read_result` 仍只消费原 Result，授权与发布规则不变。

Assessment 继续只判断用户要求是否在当前职责内得到回答。中间事实成果可以诚实保留未决缺口，但缺口不能自动证明最终问题已回答；最终候选若承认核心对象、含义或范围未确定，不能再用相近观察冒充目标结论。真实空结果可作为有效答案，零值、空数组或字段缺失本身不触发通用 HIL 或额外审计。领域澄清和业务口径由 Agent 与 Skill 决定。

工具在 `prepare` 阶段被拒绝，表示没有执行操作，不计作失败产物操作，也不启动产物修复计数。文件检查通过时，若内容评估 Gap 仍开放，也不能据此清空修复过程。

产物修复检查只适用于当前步骤明确需要文件交付或拥有已绑定产物目标的情形。全局任务 profile 中的产物 kind/format 提示不赋予步骤交付职责；生成步骤进度策略时，仅向有此职责的步骤传递这些产物约束。没有文件交付责任的事实步骤即使计算失败，也沿原工具证据、计算就绪与 Assessment 路径修正，不消耗产物修复窗口。正式产物步骤仍保留现有修复进度、检查和评估机制。

### 按步骤恢复，保留累计预算

有交付归属的 Gap 仅绑定原目标的替代生产步骤及其新前置依赖，不把独立目标和下游步骤纳入修复范围。无交付归属的采集边界以替代步骤图作为修复范围。每个新步骤只收到所选 Result 对应的完整原生工具调用与结果，以及本步骤已激活的 Skill；历史拒绝草稿不成为所有前置步骤的事实或交付义务。相同步骤的中断恢复仍保留其完整已提交交换。

上下文裁剪与预算累计分开处理：历史工具调用身份继续参与预算计数，不能通过换步骤或裁剪正文重置检索预算。Gap 的累计修订预算、独立 Plan Revision Assessor、候选 Assessment 和最终交付链路保持不变。

### 产物用途、分段创作与候选检查（2026-11-18）

Run `1d32c4c7` 暴露了两个不同边界的语义损失：唯一同格式的实验文件被自动推断为交付目标；物理检查就绪又被当作收尾信号，将仍在创作的模型切入较小输出预算。下一轮 `09712508` 的 16 次写入伴随 16 次检查，放大了模型回合与累计上下文。

当前修复复用现有主链，不增加工具、表或独立产物生命周期：

- 用途与内容完整性由 Agent/Skill 判断。Runtime 仅接受现有 `deliveryTargetId`、命令 `outputBindings` 或版本化 `work_product_progress.delivery_target` 的显式选择，再核对已观察版本、哈希、大小与目标兼容性。只有一个同格式文件也保持未绑定；文件名不产生目标归属。
- `CurrentDecisionView.currentGap.unboundDeliveryTargetIds` 从当前叶的准入目标和真实绑定派生，进入候选就绪判断及决策摘要。它是投影，不是新增 GoalGap 状态机；未绑定目标与已发生的内容评估失败仍分开表达。
- 普通分片写入后继续现有创作预算，不逐片安排自动检查，也不因物理检查成功请求 `current_step_evidence_complete`。Agent 可以主动检查中间版本；检查不会使后续创作预算缩小。
- 对模型提交的正常候选，Runtime 通过同一 Tool 准备、Action、Result 路径补齐当前已绑定版本所缺的物理检查，然后把同一候选与新回执交给既有 Assessment，无需额外模型回合重写候选。保留原有回执拥有的自动候选路径。一次检查批次中每个路径只检查一次，避免无哈希的历史回执被反复当作新版本。
- 物理检查通过不代表内容通过。拒绝仍沿现有候选修复、canonical Assessment、GoalGap、Recovery 和 TerminalCommitter 运行，保留完整授权工具。后续写入使旧版本的检查或声明失效；不会继承旧版验收。
- 同一步骤恢复时，从原有已提交事件还原工作产物观察与显式声明，不重放外部效果。替代叶仍只继承 Admission 选中的原生交换，不继承旧叶的目标归属声明。
