# GoalPlan 渐进式轮次规划与 Steer 设计

状态：设计方案，尚未实施或完成验收

日期：2026-11-08

## 1. 要解决的问题

复杂任务的后续做法常常依赖尚未取得的材料或研究结果。AgentLoop 应允许用户目标完整保留，而首轮只规划并执行有明确价值的前置工作；取得证据后，再决定下一轮如何推进。每个实际执行的步骤仍须属于已准入的 Plan。

用户还应能在 Run 执行中继续输入。用户先把消息放入输入框上方的待处理队列，点击某条消息的 **Steer** 后，消息进入当前对话和 Run，在可恢复的安全边界被处理；必要时修改目标、当前 Plan 或下一轮安排。

核心合同：**全局目标有唯一权威；每一轮有明确可验收的工作范围；已接收的用户指令不会在终态前丢失；所有执行仍经过 Plan Admission、证据评估和终态提交。**

本文是对 [Goal Loop 与多轮执行设计](GOAL-LOOP-AND-ROUND-EXECUTION-DESIGN.md) 的后续方案。与其他设计或历史状态描述不一致时，实施前以当前代码和迁移事实为准；本文描述目标合同，不宣称已实现。

## 2. 当前实现与缺口

代码静态检查显示：

- Runtime 已有 `Run → Round → Plan → Step → Assessment` 和 Round Result。当前 Plan 的活动 leaf 都完成且满足后，若仍有开放目标或 Gap，`decideRoundProgress` 可选择 `next_round`；下一轮 Planner 能收到前轮摘要、开放目标和 Result 引用。
- 现有集成测试覆盖模拟 Planner 将两个交付目标分两轮完成，并聚合结果；它不证明真实模型能主动选择“单个最终交付目标，先仅研究，后根据事实规划”。
- 首轮 Admission 的目标范围对多个目标和单个目标处理不同；Planner 指导也要求目标绑定。因此不能假定只有一个最终交付目标时，一个完全不绑定该交付目标的研究 Plan 已可作为首轮启动。
- Planner 可表达研究 leaf 和后续交付 leaf，但这与“研究后才确定下一轮 Plan”不同。Round 的完成判断目前主要基于当前 Plan 的 leaf 与开放目标/Gap；尚需明确表达阶段范围、阶段成功条件和下一轮依据。
- Desktop 活动 Run 时禁用输入并隐藏发送按钮；普通会话入口创建 Run，现有 Human Loop 回答绑定明确的请求。架构文档中的 Run messages 接口是目标，不是现成功能。
- Canonical State 已有 revision/CAS；Round 提交和 TerminalCommitter 已有事务。增加 Steer 后，必须让消息接收、影响当前执行及最终提交共享可验证的顺序，不能仅把文本追加到 UI 或内存。

本文没有检查特定生产 Run，也没有通过真实模型、已安装 Desktop 或生产数据库验证上述目标行为。

## 3. 核心对象与权威

### 3.1 目标、轮次与 Plan

`CanonicalRunState` 仍是 Run 的目标、用户约束、交付目标、Gap、进度和终态的唯一权威。保留原始输入及可追溯的用户修订；Plan 是满足当前目标的执行方案，Result 是事实，Assessment 是判断。对目标的变更通过同一个状态写入路径和 revision CAS，不建立第二份可独立修改的目标真相。

轮次规划是当前目标上的**有版本的推进决策**，不是固定的多轮剧本。每次只承诺当前轮可确定的工作：

- `purpose`：本轮推进什么，以及与全局目标/开放 Gap 的关系。
- `scope`：本轮承担的目标、前置事实或可评估的研究问题；可以不拥有最终交付目标。
- `completionBoundary`：本轮应形成什么可评估结果、所需证据和未解决事项如何表达。
- `inputs`：可使用的用户来源、既有 Result 与版本；引用保持授权和有效性。
- `continuation`：本轮结果如何用于下一次决策；只描述意向和依赖，不虚构未知结论或预定必经轮数。
- `basis`：产生此决策的 canonical revision、用户消息、Gap 和事实引用。

这些字段可作为 Round 记录中的版本化决策与证据引用，最终 schema 随实施确定；与全局目标冲突时以 Canonical State 为准。本轮只研究不等于目标已经完成；不得为了准入伪造交付目标或接受结果。

### 3.2 三层关系

| 层次 | 回答的问题 | 何时确定 |
| --- | --- | --- |
| 全局目标 | 用户最终要什么，有什么约束 | 初始理解及后续明确用户修订 |
| Round 推进决策 | 当前轮要解决什么，何时能够收口 | 当前轮规划前，变化时重新决策 |
| Round Plan | 当前轮中哪些可执行步骤可达成该范围 | 每轮执行前，必要时修订并重新准入 |

普通简单任务可在一轮内完成；不强制拆出研究轮，不固定研究、生产、验证模板。首轮应直接形成合适的可准入 Plan，而不是依赖反复失败后修补。

### 3.3 阶段性结果

Round Result 引用已经提交的 Step Result、Assessment、证据、Plan 和 canonical revision，说明本轮目标贡献、剩余 Gap、未确定事项及推进依据。研究材料形成的新事实能支持下一轮，但不能因工具成功、摘要或模型结论就直接认定全局目标完成。

## 4. 渐进式轮次规划

### 4.1 进入首轮

1. 解析用户输入及授权来源，初始化 canonical 目标、约束、交付目标和已知 Gap。
2. 在有足够信息时决定当前 Round 范围。对复杂任务允许本轮只获取前置事实；对普通任务可直接覆盖最终交付。
3. Planner 依据 canonical 状态和本轮范围生成最小可执行 Plan。研究步骤应有明确问题、合法来源、证据合同、停止条件与可评估结果。
4. Admission 检查本轮范围的完整覆盖以及全局约束、依赖、能力、来源、权限和副作用。当前轮不承担的终态目标保持开放；目标覆盖规则针对明确范围，而非按目标个数推断范围。
5. 正式持久化轮次决策与 admitted Plan 后启动执行。上下文不足时按现有 HIL/恢复机制等待，不能把不可执行的模糊计划当作已准入。

一个轮次是否可以不拥有交付目标，要由其明确的前置目的、可评估结果和对开放目标/Gap 的关联决定，而不是仅因为 `targetIds: []`。Plan 不得越权，也不能通过缩小本轮范围弱化全局约束。

### 4.2 每轮收口和下一轮决策

当前轮 leaf 已完成且 Assessment 满足当前轮合同时，统一进度协调器基于最新 canonical revision 和持久证据决定：

- `continue_round`：本轮尚有可执行的步骤或受控修复。
- `revise_plan`：新事实或用户意图使本轮 Plan 不再适用，保留有效结果，修订并重新准入。
- `next_round`：本轮阶段结果可提交，全局仍有开放事项，且有明确的事实驱动的下一步；原子提交轮次结果、进度决策和下一轮准备状态。
- `complete_goal`：所有阻塞目标、约束和交付证据均满足，交由 TerminalCommitter。
- `wait`：需要用户澄清、授权或外部条件，记录可操作恢复条件。
- `stop`：取消、不可恢复、预算耗尽或无进展；如实保留阶段成果和原因。

现有代码的 `continue_round / next_round / complete_goal` 是当前实现；其余是拟议统一协调结果，不代表已存在对应状态。可以通过现有控制流实现，但各出口必须回到相同权威检查。

下一轮 Planner 必须能读取前轮正式 Result 引用及必要证据，而不只看可能截断的摘要；引用须重新校验身份、版本、权限与适用性。对前轮的事实、新旧用户要求冲突和不确定性要可追溯。不要仅凭摘要推导事实，也不要为了规划便利重新执行已完成的外部副作用。

### 4.3 预算与无进展

延续 Run、Round、Gap 和模型调用预算；新轮、Plan 修订或 Steer 不自动重置同一问题的累计预算。真实的新证据、解决的 Gap 或可验证的状态推进可构成进展；新 Plan 文本或新 Result ID 单独出现不证明进展。需要基于证据内容及变化建立稳定判据，避免现有仅凭引用身份比较导致重复结果被误判为进展。预算耗尽或无进展时保留部分成果和开放事项，不报告目标完成。

## 5. Steer 产品交互

### 5.1 待处理队列

活动 Run 时，输入框仍可输入；发送将文本加入输入框上方、归属当前会话的待处理队列，尚不进入 Run、不影响执行。每条提供 `Steer`、编辑和删除，允许多条；点击某条 `Steer` 后才将该条提交至活动 Run。停止任务与发送保持独立。运行时 model、Runtime 等已绑定配置不随消息变更。

```text
Agent 正在研究材料……                  [查看本轮计划]

待处理
  重点分析华东，最终输出 PDF       [Steer] [编辑] [删除]
  加入去年同期对比                 [Steer] [编辑] [删除]

输入补充要求……                        [加入队列] [停止任务]
```

队列是用户草稿，不属于模型上下文；需要按账户和会话隔离并持久化，刷新或重新打开后恢复。实现可优先使用现有 Desktop 账户作用域存储，经确认其持久性、并发及清理语义后再决定具体位置；不可把凭据写入队列。首版仅支持文本，附件需另行设计来源绑定、版本和授权。

### 5.2 点击 Steer 后

- 客户端为该条生成稳定请求 ID，在提交中禁止重复编辑、删除和重复点击；网络失败或结果未知时用同一 ID 重试或查询。
- Runtime 确认持久接收后，队列项变成对话中的用户消息，标记“已接收，等待处理”；处理后显示“已应用”“已回答”或“需要澄清”。在途期间可展示发送状态，但不能把本地渲染当作已接收。
- 调整 Plan 时显示简洁的调整说明及可展开的当前计划和变更；回答进度不强制展示 Plan 变化。
- 多条被点击的消息以服务端确认的接收顺序消费。等待中的队列项仍可编辑/删除；已接收消息不提供表面撤回，除非后端实现有竞争控制的撤回合同。
- Run 已终态时，未提交的队列项保留，由用户选择作为新会话消息发送；不自动创建新 Run。若点击与终态竞争，依据服务端返回结果确定属于当前 Run 还是保留在队列，不能丢弃或自动转发。
- Run 等待 HIL 时，普通消息可作为补充意图，但不能自动视为授权、选择或对已有请求的回答。HIL 的回答仍走绑定 requestId、revision 的既有合同；两者对同一问题产生冲突时，保留请求并明确澄清。

刷新、会话切换、连接中断后，UI 从 Runtime 持久消息与事件恢复已接收状态，结合本地待提交队列去重；不得依据 SSE 或乐观 UI 单独声称消息已生效。

## 6. 消息协议与持久化

### 6.1 消息和状态

拟增加 Run 输入消息的持久化记录，以 Runtime 所属数据库为权威，至少包含：

- `messageId`、`runId`、`conversationId`、发送者、稳定 `requestId`、内容、服务端单调接收顺序及时间。
- 状态：`accepted`、`processing`、`applied`、`answered`、`needs_clarification`；另需明确处理失败及 Run 已取消/失败时未处理消息的终结状态和用户可见原因。状态命名在实现时与现有模型统一。
- 消费依据：消息位置、canonical revision、Round/Plan/Step 和处理决策；可引用计划修订、回答或 HIL 请求。原始用户文本不可变，目标投影可版本化更新。

`accepted` 只表示持久接收；`applied` 表示决策已提交到权威状态，并不代表所有后续工作已经完成。对于只提问的消息，记录有证据依据的回答，不无故改变目标。对含糊、矛盾或超出授权的指令记录澄清/等待，不能编造意图或默认扩大权限。

对同一账户、Run 和 requestId 设置唯一性；同键同内容返回原结果，同键不同内容返回冲突。事件是可重放投影；消息和处理决策由持久记录支持。输入、事件、日志和模型上下文遵循现有数据保护策略，不记录密钥。

### 6.2 API 与 Runtime 路由

目标接口可采用：

```text
POST /v1/runs/:runId/messages    { requestId, text }
GET  /v1/runs/:runId/messages    按游标读取消息与处理状态
```

Desktop 和 Multi Runtime 的公开接口经各自现有认证、账户和 Router → Host → 所属 Runtime 路径转发；具体 URL 由现有接口风格决定。服务端校验 Run 所有者、会话、Runtime 归属、输入大小和允许状态；请求不得选择其他账户的 Run 或改变 Run 原 Runtime。Run 已终态时返回明确的终态冲突，不自动创建新 Run。

请求响应至少返回消息身份、接收顺序和状态。进程内唤醒只作优化：可靠性依赖持久队列及 Runtime 恢复扫描，不依赖进程内回调、SSE 或客户端在线。

## 7. 安全边界与 Step Post

### 7.1 何时处理

Steer 不应只在 Step 完成后处理。统一检查点至少包括：

1. 初始意图解析及规划期间：下一次规划、Plan Admission 和任何执行前检查；若当前模型调用基于旧版本，结果可保留为诊断，但不得按旧版本直接准入或执行。
2. Step 开始前、模型响应提交后，以及启动下一批工具或外部副作用前。
3. 当前工具/并行批次结束并记录结果后；执行中的操作不能被视为自动撤销。
4. Step Post、Assessment/Step Result 发布前，以及 Plan 修订、Round 决策和终态提交前。

实现应在调度下一次动作与检查消息之间建立持久顺序/版本栅栏；仅在内存中先查一次队列不能消除并发窗口。已启动的外部动作根据既有 Action、receipt 和 recovery 合同处理；执行结果未知时不得重放。并行批次按既有调度边界处理，后续尚未启动的动作需再次检查最新依据。

### 7.2 Step Post 的职责

Step Post 是执行收口与推进决策的协调边界，不是额外的模型总结步骤，也不替代现有 Assessment：

1. 保存已完成的模型/工具 Action、结果、证据和未知副作用状态。
2. 处理截止边界前已接收消息，取得最新 canonical 状态；保留消息与决定的关联。
3. 对照原 Step 合同和最新目标判断证据适用性。必要时先完成针对原合同的 Assessment，再对新目标单独判断；不能把旧 Assessment 直接当作新要求已满足。
4. 选择继续当前 Step、提交有效 Step Result、修订 Plan、切换 Round、等待或停止。修订须经过现有 Admission、版本检查与持久提交。
5. 已完成事实不被抹掉；受影响的结果标记不再适用或需重新评估，不能重复执行已确认副作用。

为简单任务避免额外模型调用：进度提问和明确的确定性状态变化可走合适的确定性路径；需要解释用户语义或重规划时才调用模型。领域研究方法属于 Skill/Planner，不写入通用工具或 UI。

### 7.3 Steer 的处理结果

| 用户意图 | 期望动作 |
| --- | --- |
| 询问进度 | 基于持久证据回答；原任务继续 |
| 补充约束 | 提交目标状态修订，判断当前 Plan 和证据适用性 |
| 改变范围或交付 | 明确修订目标，受影响 Plan 重新准入；不能静默删除旧要求 |
| 与原要求冲突或含糊 | 记录冲突并请求澄清；必要时等待 |
| 请求停止 | 使用现有协作式取消，处理已启动动作与未处理消息 |

“回答进度”与正常执行的调度需要避免并发写入或阻塞终态：由同一 Runtime 协调，在可用边界产出回答；不为一条普通提问创建独立的目标真相或绕过权限的并行 Run。

## 8. 一致性、竞态和恢复

### 8.1 接收与终态的线性化

消息接收和完成提交必须使用数据库可证明的同一 Run 串行化机制：例如事务内锁定 Run 控制行并验证状态，或使用版本 CAS / 原子条件更新；各数据库的具体实现和隔离级别须实测，不能只依赖进程锁。

- 接收先于完成：消息获得接收序号；最终完成事务必须看到并处理所有已接收消息，或因存在未处理消息而退出完成流程。
- 完成先于接收：接收请求返回终态冲突；客户端保留队列项，不把它展示成当前 Run 已接收。
- 重试在完成之后到达但该 requestId 已接收：仍应返回此前的幂等结果，而不是误判为新消息。
- 成功、caveated 完成、Round 转换等所有提交入口都需统一检查；不能只在普通成功路径加检查。
- 取消和失败可能在已接收消息尚未应用时发生：持久化明确的未处理终结结果及原因，UI 可见；不承诺失败/取消后仍执行，也不能把消息丢掉或复活 Run。

### 8.2 单消费者与过期工作

按 Run 顺序领取消息，使用租约/所有权与幂等处理记录；不允许多个 Worker 重复应用同一消息。目标修订、消息处理决定和消费位置在同一事务中提交，或采用可证明幂等且可恢复的协议。canonical CAS 冲突应重新读取并重新判断，不能直接套用基于旧状态的模型决策。

规划/模型/Assessment 在途中发生 Steer 时，调用结果带所基于的 revision 和消息水位。消费前核验：过期决策不得覆盖新目标或启动后续动作。对于已启动的工具，保留真实 receipt 和恢复语义；过期并不代表它未发生。

### 8.3 重启与迁移

崩溃后依据持久消息顺序、处理状态、租约、Action/receipt、Round 和 Plan 恢复；处理中的消息重新领取前确认先前决策是否已提交。未确认外部副作用走现有 recovery，不靠重放解决。HIL、规划恢复和下一轮恢复也需读取相同消息水位。

在 SQLite、PostgreSQL、TiDB 的版本迁移中增加必要表、索引和约束；历史数据保持原事实，不伪造历史消息或 Round 结果。对已有活动 Run 的升级策略、迁移失败的前向恢复及是否需要先排空旧 Worker，在实施前按实际部署能力确定并测试。切换后保持一条权威读写路径，不建立长期双写或隐式 fallback。

## 9. 端到端案例

用户：“研究我上传的材料，识别企业数字化转型的主要问题，并制作有针对性的行动方案。”

1. 全局状态保留上传来源、行动方案目标及用户约束。
2. 第 1 Round 只承担“研究材料、形成有证据支持的问题清单”。Plan 仅含可以准入的材料读取和研究工作，最终方案目标仍开放。
3. 执行中用户把“重点关注华东”加入队列，点击 Steer；消息先显示已接收。当前工具结束后，Runtime 保存结果，判断材料与目标范围的影响，修订当前研究 Plan 并重新准入。
4. 第 1 Round 根据有效材料提交问题清单及证据引用；如果材料不足以支持华东分析，则保留缺口或向用户说明，不能虚构发现。
5. 第 2 Round Planner 使用真实研究结果决定方案结构、行动和优先级；用户原始要求与新增范围一同保留。
6. 最终 Assessment 按最新目标检查方案与证据，TerminalCommitter 在确认没有待处理的已接收消息后提交。

这是拟议验收案例，**不是已完成的真实 Run**。

## 10. 实施顺序与交付

### 阶段 A：合同与现状验证

- 用真实模型和持久化 Run 复现“单交付目标、仅研究首轮”的准入和行为；记录 Plan、事件、结果、Assessment、轮次及终态。
- 定义 Round 范围和 canonical 修订、消息水位、进度决策及存储迁移合同，梳理所有执行/恢复/终态入口。
- 确定 SQLite、PostgreSQL、TiDB 可实现的序列化手段及当前部署拓扑；先用并发实验验证。

### 阶段 B：渐进轮次与 Step Post

- 实现明确 Round 范围、仅前置研究的单目标准入、阶段 Result 和基于证据的下一轮决策；调整 Planner 合同，使其不再要求本轮覆盖全部全局目标。
- 统一 Step Post 和推进出口，保留现有 Assessment、Admission、Action 与 TerminalCommitter 职责；实现有效证据复用、版本栅栏和进度判据。
- 本阶段先不以 Steer UI 代替缺失的 Runtime 语义。

### 阶段 C：Run 消息与安全消费

- 落地消息持久化、API、认证路由、接收顺序、幂等、恢复、状态及事件。
- 接入规划、工具、Step Post、Round 和所有终态检查点；覆盖版本冲突、取消/失败和外部副作用。
- 纯文本先贯通 Desktop 与 Multi Runtime 的所属 Runtime；不自动改变能力或授权。

### 阶段 D：客户端与真实验收

- Desktop 与 Multi Runtime 会话加入队列、Steer、状态恢复、Plan 变更提示和 HIL 区分；待处理草稿按账户/会话持久化。
- 浏览器/截图验收宽窄布局及刷新、断网、队列和 HIL 交互；构建或单元测试不替代视觉验收。
- 在实际运行的目标 Runtime 重建并重启相关组件后，使用真实模型与真实来源执行完整案例；区分源码、测试、安装包、部署和实际 Run 证据。

各阶段可以拆分提交，但不将部分链路标记为已具备完整 Steer。桌面安装包或生产发布需单独执行对应构建与部署验收。

## 11. 测试和验收矩阵

### 渐进规划

- 单最终目标：研究专用首轮通过 Admission，最终目标保持开放；第二轮真实使用首轮 Result 与证据，最终只在目标满足时完成。
- 多目标和单轮简单任务不回归；超出本轮范围、缺少目标关联、无证据或无法评估的研究步骤不能冒充有效推进。
- 新事实改变下一轮方案；材料不足进入明确等待/有限结果，不伪造证据。重复相同事实但更换 Result ID 不应无限推进；新证据确实能解开 Gap 时不误判无进展。
- Plan 修订保留用户约束和适用结果；历史 Round、最终聚合、来源授权及证据版本正确。

### Steer 与竞态

- 规划中、模型生成中、工具运行中、工具批次之间、Step Post、Assessment、Round 切换、最终提交前分别提交消息；验证其实际生效边界和完整轨迹。
- 同键重复、异内容冲突、网络断开后重试、乱序点击、多客户端、并发接收与完成、取消/失败、旧模型响应迟到均可确定结果。
- 工具已启动、已成功、结果未知和副作用未确认分别覆盖；不得重复执行或声称已撤销。
- 消息持久后到处理前崩溃、处理事务中崩溃、Plan 修订后崩溃、Round 切换和终态提交时崩溃均能恢复，不重复应用、不遗漏已接收消息。
- HIL 等待期间补充消息与回答竞争；普通消息不能构成授权。Run 终态后的草稿保留并由用户决定下一步。
- 所有最终提交入口均验证消息水位与 canonical revision；先接收的消息不被成功终态越过。

### 产品和真实环境

- 会话切换、刷新、网络重连、账户隔离、原 Runtime 绑定、窄屏展示、队列编辑删除与状态无重复。
- 在 SQLite、PostgreSQL、TiDB 实例上验证迁移、约束、锁/CAS 和并发语义；分别报告未覆盖的环境。
- 真实 Run 按 `Run → 用户消息/接收顺序 → Round 决策 → Plan/Revision → Tool evidence → Assessment → Round Result → TerminalCommitter → Outcome` 核对，并检查最终交付内容；UI 和模型文字不单独作为完成证据。

## 12. 待实施时确认的具体选择

- Round 范围和阶段结果的精确 schema、与现有 Canonical State revision 的引用方式，以及哪些决策需由模型提出、哪些由内核确定。
- 各数据库的事务锁/CAS 实现、消息领取租约以及旧 Worker 升级切换方式。
- 会话草稿的账户作用域存储和多窗口冲突策略；消息状态在现有事件投影和查询 API 中的具体形状。
- 对正在输出的模型流如何呈现“被新指令取代”的草稿；不得把部分流当作最终答案或将不完整工具 JSON 执行。
- 涉及新的附件、能力、外部授权、跨会话转移或复杂撤回的后续合同；首版文本 Steer 不隐式授予这些能力。
