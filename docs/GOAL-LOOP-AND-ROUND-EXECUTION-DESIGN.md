# 目标循环与多轮执行设计方案

状态：分阶段实施中，核心多轮 Goal Loop 已接入，部署验收仍未完成

日期：2026-11-05

## 1. 设计结论

在现有 `Plan → Step Loop → Assessment → TerminalCommitter` 外增加持久化的 Goal Loop。一个 Run 对应一个用户目标，可以包含多个 Round；每轮有规划、执行、评估和轮次结果。轮次与目标判定决定：

1. 本轮未完成：在当前轮内继续执行、修复 Plan 或修复规划。
2. 本轮完成但目标未完成：提交本轮结果和目标缺口，创建下一轮并重新规划。
3. 本轮完成且目标完成：提交本轮结果，再提交整个 Run 的最终结果。

等待用户或外部条件、取消和无法继续是额外的运行控制出口，不应强行归入上述正常推进分支。目标循环的核心契约是：**初始规划、执行或评估出现问题时，Run 保留用户目标、已取得的证据和可恢复状态；仅在整体目标满足后提交最终完成。**

```text
用户目标 → Run / Canonical Goal State
                 ↓
            创建或恢复 Round
                 ↓
       Plan → Step Loop ↔ Step Assessment
        │                         ↓
        └─ 规划恢复       Round / Goal Assessment
                                  ↓
              ┌─────────── 进度判定 ────────────┐
              │ 本轮继续 │ 提交本轮并开始下一轮 │ 目标完成 │
              └──────────┴──────────────────────┴──────────┘
                   等待 / 停止 / 取消为独立出口
```

本方案延续 [用户目标、结果验收与恢复契约](RUNTIME-GOAL-RECOVERY.md)、[分层渐进式 Plan 设计方案](HIERARCHICAL-PROGRESSIVE-PLAN-DESIGN.md) 和 [统一 Runtime Result 契约](UNIFIED-RUNTIME-RESULT-CONTRACT.md)。若既有文档描述单 Plan 行为，以实际代码为现状，本设计是拟议演进，不声称现有功能已经支持多轮。

## 2. 当前边界与问题

以下是静态代码分析得到的现状，不代表对真实失败比例的统计：

- `packages/agentloop/src/planning/planner.ts` 已有有界的合同修复；Plan 仍须通过解析和准入。初始规划失败时，正式 Plan 可能尚不存在。
- `packages/agentloop/src/runtime/run-service.ts` 的执行修复主要围绕已有 Plan、Step 和评估失败；初始规划失败可能进入 Run 失败处理。正常执行、人工恢复和 Plan 修订恢复存在多个完成提交入口。
- SQLite `packages/agentloop/src/storage/database.ts` 与 TiDB `packages/agentloop/src/storage/tidb-schema-definitions.ts` 均对 `plans.run_id` 设置唯一约束；`getByRun` 和当前 Plan 查询也假定单 Plan。
- `planning/admission.ts` 要求 Plan 的目标绑定精确覆盖 canonical delivery targets；单轮仅处理部分目标不能直接通过现有合同。
- `runtime/canonical-run-state.ts` 当前绑定一个 Plan，步骤以 Step ID 索引；最终就绪要求活动步骤满足、Gap 关闭且交付目标已接受。
- `TerminalCommitter` 检查评估并提交最终状态；`RunOutcomeRepository` 同时将 Plan 和 Run 标记完成。终态 Run Result 当前以该 Plan 的活动叶子结果为输入。

上述边界说明：只在 TerminalCommitter 后加循环无法覆盖初始 Plan 失败，也无法正确表示一个 Run 的多轮 Plan。实施前应从近期持久化事件抽取失败样本，验证高频根因、规划尝试和实际用户影响，不能把代码推测当成线上统计。

## 3. 核心对象与不变量

### 3.1 Goal 与 Canonical State

Run 保持原始用户请求、交付目标、明确约束、授权范围、目标状态及尚未解决的 Gap。Plan 是执行方案，不能在重新规划时删除或弱化用户要求。用户后续修改要求必须记录为明确的用户决策。

既有 CanonicalRunState 是演进基础，不建立相互竞争的第二份目标真相。全局目标与 Gap 跨轮保留，当前活动 Plan / Step 归属当前 Round；历史结果、证据及目标贡献可追溯。Step 身份在多 Plan 下必须使用 `planId + stepId` 等有作用域的身份。

### 3.2 Round、Plan 与 Revision

Round 是一次有明确推进边界的工作，记录轮次身份、承担的目标或 Gap、状态、Plan、结果、决策及预算。Round 在规划前创建，因此无正式 Plan 时也可保存诊断、等待和恢复状态。

一个 Round 使用一个主要 Plan；当前方案仍适用时，沿用本轮 Plan Revision 修复失败步骤。已经形成可复用的阶段结果，且剩余目标需要新的分解、事实或执行路径时，提交本轮并启动新 Round。不得仅因重复失败就新建轮次或重置预算。

### 3.3 Round Result 与 Goal Gap

Round Result 是内部提交的阶段结果，至少引用本轮有效结果、证据和评估，记录目标贡献、未完成事项、原因、不确定性和后续 Gap。本轮提交不等于 Run 完成或对外发布；用户界面可展示有明确标识的阶段进度。

Goal Gap 保存目标级或步骤级的未满足条件、证据、处理历史和累计预算。同一缺口跨轮和 Plan 修订保留身份与历史；换 Step ID 或创建新轮次不能重置次数。不得虚构证据、静默丢弃缺失事实、削弱明确来源或交付要求。

### 3.4 准入与交付

每个实际执行的 Plan / Step 仍须满足其作用域内的权限、依赖、来源、证据和副作用约束。轮次范围准入允许本轮只承担部分目标或为目标提供前置结果；全部其他目标继续保持开放。最终完成仍须针对原始目标检查全部阻塞要求与交付证据。

已有 `completed_with_caveats` 语义需要明确迁移：只有原有合同允许的非阻塞不确定性才能作为 caveat；阻塞目标、明确的严格来源要求和未确认外部副作用不能靠 caveat 转成完成。

## 4. 进度判定与控制出口

判定由统一协调器基于持久化状态、评估及证据作出。模型可解释问题和提出方案，内核负责约束可用动作并验证引用、状态和权限。

| 决定 | 前提 | 动作 |
| --- | --- | --- |
| `continue_round` | 本轮未达到提交边界，且存在明确、可执行的继续或修复动作 | 恢复 Step、修订 Plan 或修复本轮规划 |
| `next_round` | 本轮结果可提交，存在具体未解决 Gap，且下一轮有基于新事实、能力或策略的推进理由 | 原子提交轮次结果和目标状态，创建下一轮 |
| `complete_goal` | 本轮结果可提交，全部阻塞目标、约束和交付要求得到满足 | 提交轮次结果，再进行最终终态提交 |
| `wait` | 必须等待用户回答、授权或外部条件 | 持久化可操作请求和恢复条件 |
| `stop` | 取消、不可恢复、无进展或预算耗尽 | 保留部分结果与原因；按现有 Run 终态合同提交或采用经设计的阻塞状态 |

`wait` 和 `stop` 的具体持久化状态需兼容当前 Run 状态模型；不能新增前端无法消费或无法恢复的伪状态。每个决策应保存所依据的状态版本、评估、证据、原因和预算；重复消费必须幂等。

## 5. 评估与提交职责

1. **Step Assessment**：判断单个 Step 是否满足其合同，继续复用现有规则、模型评估和证据验证。
2. **Round Assessment**：判断是否达到本轮可提交边界，说明有效成果、未完成事项及进入下一轮的依据。失败步骤不自动构成可提交轮次。
3. **Goal Assessment**：针对原始用户目标和所有有效轮次的证据，判断目标与交付是否满足。确定性事实优先使用内核和工具证据；模型判断需引用依据，不能代替实际验证。

职责分离：`Progress Decider` 决定下一动作；`Round Committer` 事务性保存轮次结果、目标状态及决策，不终止 Run；`TerminalCommitter` 仅在全局完成、失败或取消时提交终态。最终 Run Result 必须引用跨轮所需有效结果，而非仅引用最后一个 Plan。阶段结果与正式用户交付、外部发送或写入必须保持不同状态。

## 6. 规划失败与恢复

Round 在 Planner 调用前持久化。规划失败时记录结构化错误分类、位置、诊断、尝试、预算和必要的候选引用；原始模型响应和敏感上下文按现有数据保留与安全策略处理。首版优先覆盖真实样本中的高频问题，并保留未知类型：

- 结构、截断、无效引用或准入不一致：基于具体反馈有界修复并重新执行完整准入。
- 能力或权限缺失：重新检查当前授权目录；需要配置或授权时持久化等待，不得臆造能力。
- 关键用户意图歧义：只询问能够决定下一步的问题；回答关联同一 Round，幂等消费。
- 服务临时异常：分类重试并共享预算；不可重试或未知故障明确阻塞。

Planner 内部合同修复和外层恢复使用统一总预算。外围不能简单重复整体规划，也不能为相同错误不断创建新轮次。两次准入若使用不同能力或上下文，必须先诊断真实差异，再决定是否修复候选。

## 7. 数据、事务与恢复

目标结构为 `Run → Round → Plan / revisions → Step results / assessments → Round Result / decision`，最终 Run Outcome 仍只有一个。具体 schema、索引及 API 在实施阶段设计，至少满足：

- 多 Round 和多 Plan；同一轮唯一活动 Plan，修订版本保留。旧 Run 映射为单轮，保留原 Plan、评估、结果、引用和终态。
- SQLite、TiDB 以及仓库支持的其他数据库分别设计迁移和回滚或前向恢复策略；迁移需验证历史数据、外键、索引、幂等及实际支持的运行环境。
- 轮次结果、目标状态修订和下一步决策一致提交；通过版本检查、唯一约束及幂等键避免并发重复推进和重复创建 Round。
- 进程重启按持久化状态恢复：规划、执行、轮次提交后建下一轮、等待用户和最终提交分别有确定行为；已取消或终止的 Run 不再推进。
- 已确认外部副作用不重放；结果未知时进入既有 action、receipt 与 recovery 流程。迟到的模型响应或用户回复不得复活已取消 Run。
- 原有当前 Plan 查询继续提供兼容投影，同时增加轮次列表和历史详情；宿主 Run 投影也返回历史 Round 及其 Round Result。
- 新一轮重新检查当前能力、权限、来源和文件版本；历史证据须验证身份、可访问性和适用性，文件覆写不能继承旧版本验收。

## 8. 预算、进展和用户体验

设置轮次预算、同一 Gap 的累计预算、Run 总轮次 / 模型调用 / 时间或成本预算。当前实现提供可配置的 Run 最大 Round（默认 8，上限 64），并在创建下一轮的事务中为下一轮追加受控规划容量；用户确认重试仍使用独立的一次性加额。创建下一轮前比较开放 Gap、开放目标和有效 Result 引用；重复未解决状态直接以 `ROUND_NO_PROGRESS` 终止，达到上限以 `ROUND_BUDGET_EXHAUSTED` 终止。Plan 文本变化本身不算进展。预算耗尽保留阶段结果、剩余缺口和可执行的下一步，不标记目标完成。

用户界面展示“正在规划”“正在调整方案”“本轮已完成，继续处理剩余目标”“需要补充信息 / 配置”等有意义状态；不把每次内部校验失败显示为终态错误。等待状态必须有可用的回答或重新检查入口。对未执行、部分完成、不可恢复和未确认副作用如实说明。

## 9. 分阶段实施

1. **归因与统一出口**：分析真实失败事件；把普通执行、人工恢复和 Plan 修订恢复汇入统一进度判定，先保持单轮行为并验证不回归。
2. **Round 基础与初始规划恢复**：在规划前持久化 Round，支持结构化诊断、有界修复、等待、取消和重启；此阶段可暂时限制为单执行轮。
3. **多轮执行**：迁移单 Plan 限制，实施轮次范围准入、Round Result、跨轮 Gap / 证据传递和结果聚合，更新查询及客户端。
4. **目标评估与收敛**：完善跨轮目标评估、无进展检测、预算、可观测性，以真实样本验证最终任务结果和成本。

各阶段应先明确状态迁移和兼容策略，再实现与验证；阶段完成不意味着真实模型、安装环境或用户流程已经验收。

## 10. 验收与指标

至少覆盖以下端到端合同：

1. 首轮 Plan 未准入时同一 Round 记录并修复或等待，不丢失原始目标。
2. 本轮继续时复用正确 Plan、已完成步骤和证据；局部修订与新 Round 边界正确。
3. 本轮提交后创建下一轮；下一轮读取真实结果、证据和原始约束，未完成目标保持开放。
4. 本轮全部步骤完成但全局 Gap 未关闭时，不能提交 Run 完成；跨轮全部条件满足后仅提交一次终态。
5. 同一 Gap 跨轮预算不重置；重复失败、无进展和预算耗尽不会无限循环或伪报成功。
6. 用户回答、权限变化、取消、并发推进和进程重启均保持状态一致；外部副作用不重复执行。
7. 多次完成入口、旧数据迁移、单 Plan 查询兼容、Desktop 和 Multi Runtime 合同均得到覆盖。
8. caveat 不得掩盖阻塞要求；阶段产物、正式交付与未知副作用状态互不混淆。

按同一批代表性任务比较规划阶段直接终止率、最终完成率、无需重新提交的恢复率、用户询问率、耗时和模型调用成本；单独追踪约束丢失、缺失证据误报完成与副作用重复执行。验证中应区分单元 / 集成测试、真实模型 Run、实际部署与用户流程验收。

## 11. 开放设计事项

- Round 范围如何表达前置工作与多个目标的关联，并保证目标归属和证据链不被意外转移。
- 哪些现有 Recovery、HIL、Result 结构可直接复用，哪些需要支持没有 Plan / Step 的作用域。
- 历史运行中的 Run 如何在升级时兼容，及各数据库实际迁移能力与回滚策略。
- 最终结果跨轮引用的具体合同、授权与上下文压缩策略。
- 等待状态对现有 Run API、调度器、客户端及超时语义的兼容设计。

以上问题需在对应阶段结合代码和真实事件决定；不得用未经验证的假设替代实施与验收。

## 12. 初步实施与失败样本

当前开发分支已实现首轮记录、Plan 准入绑定、终态同步、规划失败结构化事件，以及 Plan 和会话意图解析各自的持久化模型调用预算。两类预算在模型调用前与开始事件一起提交，重复初始化不会增加已有预算。历史 Run 不回填轮次或预算。

对本机 Desktop 开发数据做只读汇总：一个账户 Runtime 中有 3 次 `PLANNING_ERROR`，其中 2 次发生在意图解析阶段、Canonical State 尚未初始化；另 1 次在 Plan 合同检查阶段，留下 2 次规划校验失败。样本较小，不能推断整体失败比例；未记录账号、原始输入或模型输出。

当前实现支持无 Canonical State 的意图阶段和已有 Canonical State、尚无 Plan 的规划阶段：规划错误进入 Human Loop 等待，用户确认后原 Run 获取一次有界重试预算，恢复使用已记录的上下文、时间、授权及来源版本，并重新执行完整 Plan 准入。取消、并发确认、租约失效与确认后中断有测试覆盖；本地 Runtime 和服务端对账均可恢复已认领但中断的规划。已观察到的 Memory 提交不会在恢复时重复触发；对于外部 Memory 提交成功但回执尚未持久化即进程崩溃的窗口，仍依赖 Memory 插件自身的幂等性。自动多轮已在同一 Run 内提交 Round Result、重置当前 Round 状态、创建下一轮并重新规划；下一轮 Planner 收到带轮次、Plan 版本、阶段摘要、开放目标 / Gap 和 Result 引用的 `agentloop.roundResultCard/v1`。Round 历史和宿主投影可读取每轮状态、Plan 和结果。下一轮规划失败会沿既有规划恢复链路等待/恢复，失败时 Run 终止并留下事件诊断。

该实现只提供一次用户确认后的规划重试，不能处理未配置能力后的动态授权变更，也不是多轮 Goal Loop。测试使用模拟模型；真实模型、实际 Desktop 重启交互及 PostgreSQL / TiDB 真实服务器迁移尚未验收。

## 13. 推进阶段与当前状态

1. **规划恢复与统一出口（部分完成）**：初始规划等待及一次有界恢复已接入；完成入口统一使用现有终态检查。真实模型、Desktop 重启和生产数据库仍需验收。
2. **轮次结果与目标判定（已完成核心链路）**：根据当前 Plan 与 Canonical State 区分本轮未完成、目标缺口未关闭和目标完成；最终提交仅接受目标完成，并将判定及状态版本写入 Round Result。Round Result 引用实际发布的 Step Result、对应 Assessment 和 Plan 版本，终态事务失败时一并回滚。
3. **多轮执行（已完成核心链路）**：已移除新数据库的 Run 单 Plan 约束，增加历史 Plan 保留、当前 Round 优先查询、下一轮 Round 创建 / Plan 绑定、按未接受目标进行范围准入、跨轮 Result 绑定和最终结果聚合。自动下一轮已接入 Run 调度；最大 Round 与无进展保护在 TerminalCommitter 创建下一轮前执行。旧数据库的 SQLite / PostgreSQL / TiDB 前向迁移已接入版本迁移链，但真实实例尚未验证。
4. **客户端与验收（进行中）**：Multi Runtime 已通过 Host / Router 的只读 Round API 接入浏览器恢复状态，回答卡片可折叠展示每轮状态和阶段摘要；仍需完善 Desktop 的同等阶段结果展示，验证 SQLite / PostgreSQL / TiDB 实例迁移、取消与重启竞态、外部副作用、真实模型及 Desktop 用户流程。

阶段 2 的单轮验证包括正常执行、人工恢复后的结果引用，以及终态失败时结果回滚；SQLite 版本迁移已测试。暂未验证 PostgreSQL / TiDB 实例或真实模型。
