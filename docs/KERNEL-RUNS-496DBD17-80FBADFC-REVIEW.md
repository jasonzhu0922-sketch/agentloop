### 可定位的内容交付断点

正式结果完整并不等于下一轮输入完整。事件链直接显示：

- 第 7 次正式结果包含完整字段数组；下一次请求前，seq 225 的 `context.tool_outputs_projected` 将 `/tables/0/columns` 标为 `valueOmitted=true`。
- 当前 `ContextAssembler.projectJsonReadQueries` 对所有查询值按大小分配共 12,000 字符预算。较小值先入选，9,662 字符的完整字段值因此被省略。原结果及读取入口仍持久化，但内容在模型作下一次决策前已经退出输入。
- seq 227 的第 8 次模型请求随后再次调用 JSON 读取；新值与原字段数组完全相同，新结果投影为 `valueOmitted=false`。
- 同一结果中的执行约束、已确认期间格式、实体和业务对象均完整保留。第 6 次的指标项目条件也在之后 seq 424 的投影中完整保留。所以后续所有失败不能归因于字段省略；也不能据原始结果推断每一份原文始终都在输入。

这是“读取成功 → 必要内容供下一次决策使用”的边界缺口。当前保护按整个消息大小判断，结构元数据及多个查询使主动读回的内容失去窗口保护。它不是原始证据丢失，也不是本次所有慢点的充分解释，更没有证据证明该行为仅在最后一次安装中才引入。

## 下一轮优化应改变的顶层契约

第一处内容交付断点在 ContextAssembler；更大的默认行为缺口在观察承接边界：**已有事件真源和语义投影，但原文退出仍主要依赖模型手工维护吸收声明，因此并未自动形成当前任务工作集。**

后续实现应围绕三项可验证契约推进，不能把 SQL 条件、指标名或特定 Skill 规则放进内核：

1. 主动读取返回的选定内容，在下一次决策有机会消费前不能仅因回执包络大小被降为引用。分清值、结构导航与协议元数据，并基于真实容量和当前内容依赖决定驻留；同源同版本窗口应复用，不能通过固定最近 N 条或单纯提高阈值完成。
2. 继续复用正式事件、Result、WorkProduct 与 canonical 范围，由内核维护精确且易引用的身份、版本、内容依赖；语义判断仍由模型/Skill 提议。承接、替代、问题解决与版本适用性应在正常行动中表达和校验，不引入每轮维护调用，不让模型凭空重抄不透明 ID。成功执行不能自动解决语义未知，失败写入及未知效果也不能被吸收掉。
3. 把“必须携带的内容、尚未承接观察、历史定位入口、真正必须的 Provider 延续”分别投影，执行与评估共享同一依赖基础。用本次完整路线的冻结结果做旧/新离线回放，再做固定配置隔离模型重复样本；同时考察总调用数、重复内容读取、最终答案、未解决问题与恢复等价，不能只优化字数。
