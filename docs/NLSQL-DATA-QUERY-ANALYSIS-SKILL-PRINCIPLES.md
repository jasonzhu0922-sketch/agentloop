# 基于 NLSQL 的数据查询分析类 Skill 构建原则

## 1. 文档目的

本文结合钢材市场价格 Skill 从“自然语言直接查指标”逐步演进为“上层分析方法论 + 下层受控数据访问 + 确定性计算 + Runtime 证据治理”的过程，总结一套可复用于经营分析、财务分析、供应链分析、行情分析、指标分析等场景的 NLSQL Skill 构建原则。

这里的 NLSQL 不应被理解为“让模型自由生成一段 SQL 并执行”，而应被定义为：

> 将自然语言问题转换为经过数据库语义验证的查询意图，由数据源 Skill 在受控边界内编译并执行 SQL，再把可审计的原始数据交给分析 Skill 形成与证据强度匹配的结论。

因此，系统的核心产物不是 SQL 文本，而是完整的语义与证据链：

```text
用户问题
  -> 研究问题与最小证据
  -> 数据库语义对齐
  -> 受控查询计划
  -> 参数化 SQL 执行
  -> 原始数据回执
  -> 可复核派生计算
  -> 有边界的业务结论
```

## 2. 从钢材市场价格 Skill 演进中得到的核心认识

钢材场景暴露的问题具有很强的通用性。

### 2.1 不能把整句自然语言当成一个数据库值

“唐山市河钢 HRB400E Φ8 热轧盘螺工程采购价”不是一个天然存在的指标名称，而是由城市、生产企业、品种、牌号、规格、指标口径等多个语义槽位组成。

直接对完整句子做模糊匹配，会把“自然语言理解失败”伪装成“数据库没有数据”。正确做法是先读取真实目录字段和值域，再把请求拆到已确认的语义维度中。

### 2.2 逻辑字段名称必须服从数据库真实语义

早期映射曾把大区当城市、数据来源当钢厂、报价说明当规格。这类错误即使能生成合法 SQL，也只会得到语义错误的结果。

因此，NLSQL 的首要质量标准不是 SQL 可执行，而是：

- 逻辑字段是否对应正确的业务概念；
- 物理字段是否由部署映射确认；
- 不同字段是否被错误替代或混用；
- 关联键和数据粒度是否真实成立。

### 2.3 候选发现、精确选择、原始取数、派生分析是四个不同阶段

目录样例不是完整值域，候选不是已选指标，查询返回行数不是分析结论，工具成功也不是业务完成。

钢材链路最终形成了以下分层：

1. `preflight-catalog`：确认当前数据库映射和字段语义；
2. `discover-indicators`：根据已映射的语义槽位寻找候选；
3. 精确 `INDEX_CODE` 查询：读取一个已确认指标的原始时序；
4. `analyze-series`：从原始数据生成可复核的派生事实；
5. 上层 Skill：选择分析方法并交付结论。

任何阶段都不能用后一阶段的措辞伪装成已经完成。

### 2.4 空结果必须解释为一个有作用域的查询事实

空结果至少可能表示：

- 语义槽位映射错误；
- 查询条件过严；
- 候选目录中不存在目标实体；
- 目标实体存在，但指定时间窗没有观测；
- 数据源、权限、连接器或依赖未就绪；
- 查询尚未真正执行。

只有“精确实体 + 明确时间窗”的查询实际执行并返回零行，才能形成 `no_observations`。它仍然不能扩张为“数据库没有该类数据”或“市场不存在该数据”。

### 2.5 分析方法必须适应实际数据形态

早期钢价分析容易把首末价格变化当作固定方法。但当同一天存在多个不同数值时，并不存在可直接使用的唯一日价。

合理的分析应根据实际数据形态降级或切换：

- 每日唯一值：可计算首末变化、阶段高低、波动；
- 同日多个不同值且没有区分字段：分析每日数值集合、上下界和区间移动；
- 单一观测日：只能描述该日的观测集合，不能声称趋势；
- 多序列口径不一致：分别描述，不能直接计算价差或排名；
- 样本不足：交付已有事实及限制，而不是补数或编造。

计算程序应暴露中性事实，不能替上层 Skill 决定业务方法。

### 2.6 Skill 元数据必须真实描述执行器能力

钢材取数执行器已经能够返回完整原始序列，但 Skill 元数据一度没有声明 `structured_extraction_artifact`，导致计划在 Admission 阶段被正确拒绝。

这说明 Skill 的说明文字、元数据、执行器输出和证据回执必须一致。不能为了通过校验而降低通用 Runtime 的要求，也不能声明执行器并未实际产生的证据。

### 2.7 部署故障不能被叙述成业务无数据

缺少 MySQL 驱动、数据库配置不可用、连接器参数缺失、SQL 结构校验失败，均属于执行或部署边界故障，不是业务查询结果。

数据查询 Skill 必须让这类故障在查询前或执行入口清晰失败，不能进入“无数据分析”或要求用户通过 HIL 猜测数据库事实。

## 3. 当前钢材上下层 Skill 的职责模型

### 3.1 上层：`steel-market-analysis`

当前上层 Skill 是业务分析所有者，角色为 `primary_builder`。它负责：

- 定义研究问题和用户真正要做的判断；
- 确定产品、市场、指标、时间和比较口径；
- 选择最小指标组和分析方法；
- 生成不含 SQL、表名和物理字段的受控查询计划；
- 判断多序列是否具备单位、频率、时间和业务口径可比性；
- 使用确定性计算事实组织趋势、区间、比较或风险分析；
- 区分数据观察、业务解释假设和当前证据无法支持的内容。

它不负责猜表、猜字段、拼 SQL、直接读取数据库或用模型心算替代派生计算。

### 3.2 下层：`mysql-steel-data`

当前下层 Skill 是只读数据源边界，角色为 `source_provider`。它负责：

- 暴露部署确认的目录、观测表、粒度和关联关系；
- 将自然语言中的准确目录值匹配到已映射语义字段；
- 返回有区分度的候选，不替上层选择歧义对象；
- 将精确业务 ID、日期范围和受控过滤器编译为参数化 SQL；
- 限制表、列、关联、查询范围、行数和动作类型；
- 返回原始数据、实际覆盖、截断、选择依据和证据回执；
- 明确区分未找到实体、候选歧义和指定窗口无观测。

它不接受任意 SQL，不选择分析方法，不计算涨跌、均值、峰谷或市场结论。

### 3.3 确定性计算层

`analyze-series` 这类执行器负责：

- 只消费已持久化并绑定来源回执的原始数据；
- 生成观察数、唯一日期数、每日数值集合、覆盖、极值、缺口和区间边界移动等事实；
- 对不可计算情形返回 `computable: false` 和明确 caveat；
- 让每项派生事实能够回指原始查询回执；
- 不选择业务叙事，不把统计相关写成因果。

### 3.4 Runtime

Runtime 应只承担通用治理职责：

- Skill 发现、能力绑定和 Admission；
- 授权、只读/只写边界和 Host 能力预检；
- Run 工作区文件持久化；
- 原始结果和计算输入的完整性绑定；
- 证据回执保存、投影和上下文传递；
- 步骤完成、修复、终止和最终 Outcome 判定。

Runtime 不应编码钢材字段、固定查询顺序、行业分析方法或某个数据库的特殊兜底。

## 4. NLSQL 数据查询分析类 Skill 的构建原则

### 原则一：按业务所有权拆分上层分析 Skill 与下层数据源 Skill

一个通用 NLSQL 方案至少应拆成两个 Skill：

```text
<domain>-analysis        上层：问题、方法、最小证据、解释和交付
<source>-data            下层：模式、语义映射、查询编译、执行和原始回执
```

若分析方法可以跨数据源复用，上层可以依赖多个数据源 Skill；若同一数据源服务多个业务场景，下层不得内置某个分析报告的业务逻辑。

判断规则是：

- “为什么查、查哪些指标、如何比较、结论如何表达”属于上层；
- “表在哪里、字段是什么意思、如何安全查、返回了什么原始行”属于下层。

### 原则二：先建立数据契约，再允许自然语言查询

每个数据源 Skill 必须有部署侧确认的数据契约，至少包含：

- 可访问的数据源、schema、表或视图；
- 每张表或视图的业务粒度；
- 主键、稳定业务标识和允许的关联键；
- 逻辑语义字段到物理字段的映射；
- 日期、数值、单位、频率和维度字段的含义；
- 允许的查询类型、最大时间窗、最大返回行数；
- 数据更新频率、时区和已知质量限制。

文档只能作为设计说明；运行时应以当前部署映射和 preflight 返回的数据契约为准。文档、映射和实时预检不一致时，应停止猜测并报告映射问题。

### 原则三：自然语言先转成业务语义槽位，不直接转 SQL

建议先形成一个上层语义对象：

```json
{
  "questionType": "trend|comparison|distribution|ranking|diagnosis",
  "metrics": [],
  "entities": [],
  "dimensions": {},
  "timeRange": {},
  "granularity": null,
  "comparisonBasis": null,
  "requestedOutput": null,
  "assumptions": [],
  "unresolvedTerms": []
}
```

该对象表达用户问题，不包含 SQL、表名或列名。只有经过下层数据契约确认的槽位，才能进入查询选择器。

严禁：

- 把整句自然语言作为一个指标名；
- 用相近词把一个维度自动替代另一个维度；
- 根据字段名猜测业务含义；
- 把目录高频样例当作完整值域；
- 将未解析词静默丢弃。

### 原则四：把实体发现与事实查询分开

任何依赖稳定业务实体的数据查询都应采用两阶段模型：

```text
语义字段 -> 候选实体 -> 精确业务 ID -> 事实数据
```

候选必须返回足够的区分维度，例如名称、地区、组织、单位、频率、口径和来源。只有以下条件满足时才可自动选择：

- 候选唯一；
- 未发生截断；
- 所有关键业务槽位均匹配；
- 单位、频率和对象身份明确；
- 没有被忽略的冲突条件。

否则应继续有界发现，或要求用户确认真实歧义。不得为了得到结果而偷偷删除条件、扩大时间范围或改用相似实体。

### 原则五：上层传“查询计划”，下层负责编译 SQL

上层查询计划只描述分析方法需要的数据，不携带原始 SQL。建议采用类似结构：

```json
{
  "schema": "domain.queryPlan/v1",
  "method": {
    "id": "regional-price-comparison",
    "summary": "比较两个已确认区域在共同日期内的同口径价格"
  },
  "queries": [
    {
      "id": "region-a",
      "purpose": "比较序列 A",
      "startDate": "2026-01-01",
      "endDate": "2026-03-31",
      "selector": {
        "entityId": "..."
      }
    }
  ]
}
```

计划需要限制：

- 查询项数量；
- 日期范围；
- 每项只能使用一种选择方式；
- 选择器只能使用已映射字段或精确 ID；
- `method` 和 `purpose` 仅用于审计，绝不能变成 SQL 片段。

### 原则六：SQL 必须由下层确定性编译，并默认只读

模型不应直接提交任意 SQL。下层数据源 Skill 应使用固定模板或 AST/DSL 编译器，并执行以下控制：

- 表、列、函数、连接关系和排序方式使用 allowlist；
- 值全部参数化绑定；
- 禁止 DDL、DML、多语句、注释注入和跨库访问；
- 强制租户、组织、账户或数据权限条件；
- 强制行数、时间窗、超时和分页上限；
- 查询前进行方言和结构校验；
- 记录参数化后的查询意图或查询指纹，避免泄露凭证；
- 只在确有需求时开放经过审核的有限聚合模板。

若业务确实需要开放表达式，应先扩展受控 DSL，而不是回退到自由 SQL。

### 原则七：最小充分查询，不让“能查什么”反向决定研究问题

上层 Skill 应先定义研究问题和最小证据，再请求数据。查询计划应只包含对当前结论有明确用途的指标，避免一次性拉取大量无关历史和字段。

最小充分原则包括：

- 只查询必要实体和时间窗；
- 先以轻量目录查询消除歧义，再读取事实表；
- 多指标分析逐项保留独立回执；
- 达到行数上限时拆分相邻窗口，不静默截断；
- 不因某数据容易获得就擅自改变用户的研究对象。

### 原则八：原始查询结果必须成为一等证据制品

一个可用于分析的查询回执至少应保存：

- 查询动作和来源；
- 数据契约或 schema 版本；
- 选择器、精确实体 ID 和选择依据；
- 请求时间窗、实际数据覆盖和排序；
- 返回行数、唯一实体数、截断和分页状态；
- 单位、频率、时区和粒度；
- 原始数据的持久化位置；
- caveat、失败项和可重试信息；
- 可回指本次结果的稳定 receipt ID。

模型摘要、stdout、行数、SQL 成功状态和手工复制的小段数据都不能代替完整原始结果。

### 原则九：用类型化状态表达空结果、歧义和失败

建议至少区分：

| 状态 | 含义 | 可否形成业务结论 |
| --- | --- | --- |
| `candidate_not_found` | 当前映射和条件下没有候选实体 | 否，应检查语义或映射 |
| `candidate_ambiguous` | 存在多个真实候选 | 否，应继续区分或确认 |
| `no_observations` | 精确实体在指定窗口返回零行 | 只能报告该窗口无观测 |
| `observations_available` | 已取得原始行 | 仍需派生计算后才能分析 |
| `query_truncated` | 结果不完整 | 不得作完整覆盖结论 |
| `schema_mapping_error` | 逻辑与物理语义无法确认 | 否 |
| `execution_unavailable` | 驱动、连接、权限、网络或 Host 不可用 | 否，且不能称为无数据 |
| `query_rejected` | 查询违反安全、方言或结构规则 | 否 |

这类状态应写入机器可读回执，不能只存在于自然语言错误信息中。

### 原则十：派生计算与业务解释必须分层

确定性计算层负责“怎么算”，上层分析 Skill 负责“这些计算是否适合回答当前问题”。

计算层应：

- 对输入 schema 做严格校验；
- 保留原始来源回执；
- 输出明确公式、样本数、覆盖和不可计算原因；
- 对空值、零除、同日多值、日期缺口、异常值和截断显式 caveat；
- 不做隐式补零、插值、去重、单位转换或代表值选择；
- 输出中性、可复核的 `deliveryFacts`。

上层 Skill 应：

- 从实际数据形态中选择最强但仍可辩护的方法；
- 需要时主动降级，而不是因理想方法不可用就停止；
- 不把计算摘要原样粘贴成业务报告；
- 不把相关性写成因果，不把描述写成预测。

### 原则十一：所有比较、聚合和排名都必须先过可比性闸门

跨序列分析前至少检查：

- 指标定义是否一致；
- 产品、组织、地区、市场和业务口径是否可比；
- 单位及单位换算依据是否一致；
- 频率和时间粒度是否一致；
- 日期是否存在足够交集；
- 是否有版本、汇率、含税/不含税等口径差异；
- 是否存在截断、缺口或样本偏差。

任一关键条件不满足时，只能分别描述，不能输出价差、比率、排序或汇总结论。

### 原则十二：恢复应针对真实缺口，且必须有界

查询失败后的修复应依据失败类型：

- 字段不匹配：回到 schema/preflight；
- 候选为空：检查被哪个条件排空，而不是无限放宽；
- 候选歧义：补充真实区分维度；
- 指定窗口无观测：可以按用户授权检查相邻窗口，但必须生成新回执；
- 结果截断：拆分窗口或分页；
- 计算不可用：改用数据仍支持的较弱方法；
- 驱动或 Host 不可用：在部署边界终止，不进入业务恢复。

每次重试都必须记录改变了什么、为什么改变，以及新旧查询是否仍回答同一个问题。达到预算后应明确终止，不能无限循环查询。

### 原则十三：完成判定必须绑定端到端证据链

数据查询分析任务的完成条件不是“执行过 SQL”，而是：

```text
研究问题已定义
AND 数据语义已确认
AND 查询对象已精确选择
AND 原始数据或有作用域的空结果已取得
AND 必要派生计算已完成
AND 最终答案消费了相关计算事实
AND 限制和不可推出内容已说明
```

以下均不能单独证明任务完成：

- Skill 已加载；
- preflight 成功；
- SQL 通过语法校验；
- 工具返回成功；
- 返回了若干行；
- 模型在文字中声称已分析；
- 文件已生成或被接受；
- UI 显示任务完成。

### 原则十四：Skill 元数据、说明、执行器和回执必须同构

每个动作都应回答四个问题：

1. 它接受什么受控输入；
2. 它实际执行什么边界内的操作；
3. 它产生什么证据种类；
4. 下一个消费者如何验证和使用该证据。

应建立自动校验，检查：

- Skill 声明的 evidence kinds 是否确实由回执产生；
- executor action ID 是否唯一；
- action 描述是否与真实行为一致；
- 示例、schema 和实现是否同步；
- 下层输出是否满足上层输入契约；
- 变更后 Host 是否加载了当前版本。

### 原则十五：部署能力是正式契约的一部分

NLSQL Skill 上线前必须进行 Host preflight：

- 数据库驱动及版本；
- 网络和 DNS；
- 凭证、密钥或数据权限；
- 数据库方言和编码；
- schema 映射文件；
- 所需脚本和依赖；
- 工作区读写权限；
- 超时、并发和资源限制。

缺少能力时，应在 Plan 或执行前给出明确、可运维的错误；不要让模型在多轮对话后才把依赖故障误判为查询无结果。

### 原则十六：把领域差异放入 Skill，把通用完整性放入 Runtime

领域 Skill 可以拥有：

- 指标语义；
- 目录选择器；
- 查询模板；
- 研究方法；
- 可比性规则；
- 领域输出结构。

Runtime 应拥有：

- 权限与执行授权；
- 工作区和内容引用；
- 输入完整性与版本状态；
- 通用证据保存和投影；
- 步骤、恢复和终态协议。

不要因为一个领域链路失败，就把领域字段、固定工具序列或特定报告规则硬编码进 Runtime。

## 5. 推荐的通用 Skill 结构

```text
skills/
  <domain>-analysis/
    SKILL.md
    references/
      analysis-methodology.md
      comparability-rules.md
    scripts/
      profile_dataset.py
    tests/
      test_profile_dataset.py
    agentloop.executors.json

  <source>-data/
    SKILL.md
    schema-map.json
    references/
      data-semantics.md
      nlsql-query-patterns.md
    scripts/
      source_data.py
    tests/
      test_source_data.py
    requirements.txt
    agentloop.executors.json
```

其中：

- `SKILL.md` 讲所有权、工作流、完成边界和何时使用；
- `data-semantics.md` 讲真实粒度、字段、关联和口径；
- `nlsql-query-patterns.md` 讲允许的编译模板及空结果语义；
- `analysis-methodology.md` 讲问题类型、最小证据、方法选择和降级；
- 脚本只实现确定性数据访问或计算；
- 测试验证失败边界，而不只验证正常返回。

## 6. 必须覆盖的测试矩阵

### 6.1 数据源 Skill

- 映射缺失、字段不存在和关联键错误；
- 参数化查询，注入字符不能改变 SQL 结构；
- 不支持的逻辑字段被拒绝；
- 多条件使用各自字段，不能相互替代；
- 零候选、单候选、多候选和候选截断；
- 实体存在但时间窗无观测；
- 返回行数截断和分页；
- 单位、频率、时区和实际覆盖进入回执；
- 驱动、配置、权限和网络失败不会变成 `no_observations`；
- 任意 SQL、写操作和跨库查询被拒绝。

### 6.2 分析 Skill 与计算层

- 每日唯一值；
- 同日多条相同值；
- 同日多个不同值；
- 单一观测日；
- 日期缺口；
- 非数值、空值、无穷值和零除；
- 多序列单位或频率不一致；
- 日期交集为空或过小；
- 原始结果截断；
- 派生事实可回指来源 receipt；
- 最终输出不会使用不可计算字段；
- 数据不足时能够降级，而不是编造结论。

### 6.3 端到端验收

端到端验收至少包含：

1. 一个唯一实体的正常查询分析；
2. 一个真实歧义实体，需要确认或补充维度；
3. 一个精确实体的空时间窗；
4. 一个同日多值、不能计算唯一涨跌的案例；
5. 一个 Host 依赖或权限失败案例；
6. 一个结果截断并拆分窗口的案例；
7. 一个多序列因口径不一致而拒绝比较的案例。

测试必须验证最终交付使用了哪一份原始回执和派生事实，而不只验证 SQL 或脚本退出码。

## 7. 常见反模式

- 让 LLM 直接生成并执行自由 SQL；
- 用一段超长提示词代替真实 schema 映射；
- 把整句用户请求放进一个 `LIKE '%...%'`；
- 用相近字段或相近实体“兜底”出结果；
- 把候选列表中的第一项默认视为用户目标；
- 将查询为空直接写成“数据库没有数据”；
- 把驱动、权限、连接或 SQL 校验失败写成“无数据”；
- 用行数、stdout 或模型摘要代替完整原始结果；
- 让计算脚本固定选择均值、首末值或某个代表值；
- 无视单位、频率和日期交集直接比较；
- 为通过验收而降低证据要求或伪造 evidence kind；
- 在 Runtime 中硬编码领域字段、Skill 名称和工具顺序；
- 只通过单元测试就宣称部署后的 Skill 已生效。

## 8. 构建与评审清单

### 8.1 设计评审

- 上层和下层的业务所有权是否清晰？
- 数据粒度、实体 ID 和关联键是否经过数据库所有者确认？
- 自然语言是否先形成语义槽位和查询计划？
- 模型是否无法提交任意 SQL、表名和列名？
- 空结果、歧义、截断和执行故障是否有不同状态？
- 分析方法是否能够随数据形态降级？
- 比较前是否存在明确可比性闸门？
- 每个结论能否回指原始回执和派生计算？

### 8.2 上线评审

- Skill 元数据与实际回执是否一致？
- Host 是否具备驱动、配置、权限和网络能力？
- schema-map 是否为部署当前版本？
- Skill 包是否被真实发布和加载，而不只是本地修改？
- 是否完成重启后的新 Run 验证？
- 是否区分了 focused tests、Host 验证和真实数据端到端验证？

### 8.3 运行质量指标

建议持续观测：

- 自然语言请求一次定位唯一实体的比例；
- 候选歧义率和零候选率；
- 因错误字段映射导致的空查询率；
- 查询重试次数及每次条件变化；
- 原始查询到派生计算的完成率；
- 截断结果被错误用于结论的次数；
- 无观测与执行故障的误分类率；
- 最终答案中来源回执、覆盖和 caveat 的完整率；
- 相同结果被重复读取或重复查询的次数。

## 9. 总结

基于 NLSQL 的数据查询分析类 Skill，真正需要构建的不是一个“会写 SQL 的提示词”，而是一套分层的语义与证据系统：

1. 上层 Skill 对用户问题、研究方法和结论负责；
2. 下层 Skill 对数据库语义、受控查询和原始事实负责；
3. 确定性计算对派生数值的可复核性负责；
4. Runtime 对授权、完整性、证据传递和正式完成负责。

其最重要的质量原则可以浓缩为一句话：

> 先证明“查的对象和口径是对的”，再证明“查询确实执行并取得了什么”，最后只交付“当前证据真正支持的分析”。
