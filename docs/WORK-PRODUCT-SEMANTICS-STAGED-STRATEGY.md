# 工作成果语义统一：分阶段实施与验收策略

日期：2026-09-16
状态：阶段 0、1 离线验收已完成；阶段 2、3 已实现并完成限定范围验证，当前仅接入新建文件产出 leaf，未接入 Recovery。较大回归集与类型检查仍有已知失败，不代表全仓放行；本实施切片未推进阶段 4—6。详见 [阶段 0、1 验收记录](WORK-PRODUCT-SEMANTICS-STAGE-01-ACCEPTANCE.md) 与 [阶段 2、3 验收记录](WORK-PRODUCT-SEMANTICS-STAGE-23-ACCEPTANCE.md)。

## 目标与边界

让执行、上下文投影、Assessment 和 Recovery 对已有成果、有效版本、未解决问题及交付状态保持一致。沿用现有事件、Plan、工具结果和终态提交体系；共享状态是从权威记录派生的视图，不另建一份可以独立修改的任务真相。

本策略是 `SEMANTIC-STANDARDIZATION-AND-CONTEXT-UNIFICATION-PLAN.md` 的小范围实施切片，不代表旧方案中列出的历史问题均在当前版本仍然存在，也不一次实施其全部内容。

第一批实施阶段 0、1；第二批按用户指示实施阶段 2、3。每阶段单独评审、测试并保持可独立回退，提交另由用户确认；达标后才能开展下一阶段。阶段 6 是独立后续项目，前五阶段可独立产生价值。

## 共用约束

- 轻量 Plan 保持可逐步修订；不增加全局 required-facts 调度、不改变工具授权、不为普通回答新增文件要求。
- Runtime 记录实际副作用、引用和版本；模型/Skill 判断用途、内容充分性和工作方法。模型声明不能证明文件已生成或检查已通过。
- 存在、可读取、内容充分性、检查结果、选为交付候选、实际交付分别表达，不归并为单一“成功”。
- 摘要/裁剪改变展示细节，不改变已确认事实；删除、覆盖、失效和冲突则必须改变当前有效状态并保留历史依据。
- 检查绑定对象、版本和范围。历史检查可保留；缺少版本绑定时标为未知，不能伪造 hash 或自动证明当前文件通过。
- 实验和探索允许存在；下一步建议供模型使用，不变成固定工具顺序或额外逐轮审核。
- 禁止针对 Run ID、文件名、PPTX 或某个模型写特殊恢复逻辑。

## 阶段 0：冻结基线与回放样本

**唯一目标：** 获得不依赖实时 LLM 的可重复失败样本和真实测试基线。

工作内容：

- 记录当前 commit、相关未提交 diff、Node/依赖版本、Host 加载的构建与启动方式。工作区已有大量修改，不把它们当成干净 main 基线，也不擅自覆盖或归入新提交。
- 从两个 Run 的相关持久化事件提取最小、脱敏的 fixture；记录原始 Run、事件序号、工具调用来源。历史 DB 与工作区保持只读。
- 使用可脚本化的模型响应和工具结果回放：固定“返回空回复”“执行失败”“生成实验文件”等条件，不用真实模型输出决定单元测试成败。
- 先记录当前行为；预期的新行为可用独立诊断复现，正式回归断言随对应修复进入，避免依靠跳过失败测试宣告通过。

基础样本：

| 编号 | 场景 | 必须保留的区别 |
|---|---|---|
| A | b564c522：候选 PPTX 已生成，结构校验通过，字体脚本未执行，随后空回复 | 文件存在；检查范围有限；工作与交付未完成 |
| B | d0e99198：生成脚本失败，已查清 API 不兼容，只生成实验 PPTX | 目标产物未生成；实验文件存在；修复未执行 |
| C | 命令失败但产生部分文件 | 操作失败；已观察到文件；完整性未知 |
| D | 检查 v1 后覆盖为 v2，或删除文件 | 历史检查存在；当前版本未被该检查证明 |
| E | 关键结果后追加大量无关结果，缩小投影窗口 | 关键进展仍可定位，不随展示窗口消失 |
| F | 普通问答、来源摘要、正常文件交付 | 原有成功路径不增加不必要义务 |

放行：fixture 不访问外部网络、不修改历史 Run；重复回放一致；基线失败逐项记录，后续可识别新增回归。连续空模型响应的 provider 原因不在本策略中预设。

## 阶段 1：统一客观成果观察，仅离线使用

**唯一目标：** 从原始工具结果准确重建文件事实与版本关系。

修改范围：现有工具结果归一化/读取边界、`RuntimeStepEvidenceState` 相关类型与纯归约逻辑及测试。新增字段仅在必要时采用可选、附加式记录；本阶段不改变模型输入、工具选择、Assessment、Recovery 或数据库 schema。

实现要点：

- 记录对象引用、来源调用、创建/修改/删除、可得的 bytes/hash、操作结果、原始内容引用。
- `operationStatus=failed` 不整体丢弃可信的已报告副作用；也不将失败时留下的文件当作完整成果。
- 处理同路径覆盖、删除与重建。路径相同不代表版本相同；无法确定先后或版本时保留未知/冲突。
- 从完整适用记录计算事实，再选择展示窗口；仅对当前 Run/授权依赖范围归约。

测试：A、B 的文件清单和来源正确；C 的部分副作用保留；D 的旧版本失效；重复处理同一事件不重复新增对象；同一有序事件集重复回放得到相同结果。

放行：新增回归全通过，相关既有测试无新增失败，Kernel 构建通过；离线回放可以解释每个事实的来源。此时不声称改善了真实模型执行。

回退：撤回新增纯读取/归约实现即可，不需要修改历史数据。

## 阶段 2：补齐用途与未解决问题，仍不驱动行为

**唯一目标：** 分开表示“这个对象是什么用途”和“当前到底卡在哪里”。

修改范围：成果用途、目标关联、问题记录及其持久化来源。首先复用已有明确声明；不足时，在正常模型回合中提供最小的结构化进展声明，不新增专门 LLM 评估回合，不强制每一步填写表单。

声明必须带对象/版本引用和来源。字段缺失保留 unknown；格式错误只拒绝该声明，不把整个 Run 判为失败。模型可修订用途和诊断，但不能修改 Runtime 已观察到的文件事实。

最小语义：

- 用途：输入、生成脚本、实验结果、候选交付、未知。实际“已交付”只由终态交付记录证明。
- 问题：关联对象、已观察症状、模型诊断及依据、已尝试动作、尚未执行动作、是否已验证解决。
- 有效性：用途与问题适用于哪个目标和对象版本；明确修订才覆盖旧声明。

测试：B 中实验 PPTX 与目标稿同格式仍保持不同用途；没有声明时不能靠文件名猜“实验”；“打算生成/已经写脚本”不变成“目标稿存在”；只查清错误不能变成“已修复”；新的成功执行可为问题解决提供依据。

放行：同一事实与声明集离线得到稳定状态；用途与客观事实冲突可解释；此阶段不得影响交付放行结果。涉及附加事件时，验证历史事件无新增声明也可读取。

回退：忽略附加声明记录，保留原始事实；不建立第二套独立业务状态表。

## 阶段 3：接入执行上下文，只改模型看见的信息

**唯一目标：** 每轮准确看见已有成果与真实缺口。

修改范围：`execution-context-policy.ts`、`step-execution-strategy.ts`、必要的 ContextAssembler 接入。沿用现有语义状态块，替换重复信息，不另叠一份长提示。不改变硬性完成门槛和自动恢复调度。

固定提供：目标/约束、相关成果与版本、已完成事项、未解决问题、待执行动作、下一步建议及依据。全文仍按不可变引用与有界读取取回；关键状态放在可重建的 Runtime 投影中。

测试：

- A 可见现有主题版与未执行字体脚本；B 可见生成器、明确错误、实验用途与目标稿缺失。
- 强制截断、摘要/压缩、追加无关工具结果后，以上事实与引用不消失；版本变更则正确更新。
- 用脚本化模型检查实际收到的上下文，不只测试内部 helper。
- 不要求模型严格执行唯一 nextAction；允许有依据的替代动作。
- 固定 fixture 的 context 字符/token 预算设上界，并记录相对基线差值，避免用扩大上下文掩盖缺陷。

放行：确定性回归通过；重建并启动隔离 Host，用 A/B 类任务各做 3 次新 Run 观察，外加 F 控制样本。记录真实完成率、重复探索、轮数与 token，不把少量线上成功解释为普遍稳定；若观察不支持改善，停留本阶段诊断。

回退：撤回上下文接入，保留阶段 1、2 的观察能力。测试阶段可限定启用范围；不长期维护两套事实解析器。

## 阶段 4：Assessment 共用事实，精确报告缺口

**唯一目标：** 拒绝完成时保留已有进展，并指出具体未完成条件。

修改范围：`planning/assessor.ts`、候选评估输入和相关测试。共用前面已验证的事实视图，删除被替换的重复事实推断；不借机加入额外内容审核或放宽必要交付条件。

区分事实与判定：空候选可以使整体完成判定失败，但不能反向抹去文件存在和历史检查。事实观察不足时说明“未知/未确认”，不能宣称文件不存在。检查按对象、版本和范围应用；某文件通过不能证明另一个文件通过。

测试：

- A 空候选：拒绝交付，但保留文件存在及结构检查，缺口指向空回复、未完成工作与必要检查。
- B 空候选：目标稿尚未生成，实验 PPTX 不满足目标；输出有文字也不能蒙混通过。
- D：v1 检查不证明 v2；通过检查后删除文件不能成功提交。
- F：普通问答不新增 artifact 要求，已有正常交付仍通过。

放行：规则测试与受影响的 planning/runtime 集成测试通过；无错误完成回归；隔离 Host 新 Run 的拒绝原因可由持久化事实解释。核验 Outcome 与交付记录，不以 UI 文案为准。

回退：撤回 Assessment 消费方式，保留已验证状态与上下文；不重写历史 assessment。

## 阶段 5：Recovery 继承同一状态，显式触发验证

**唯一目标：** 恢复后仍准确知道目标、成果、版本、诊断和实际缺口。

修改范围：`run-service.ts` 恢复输入构建、恢复 transcript/读取逻辑与集成测试。阶段内维持显式触发，正常执行和恢复使用同一事实归约；修订 Plan 只改变明确修订的事项。

测试：

- 在生成、诊断、检查完成等边界注入中断，恢复前后同一事件水位下的事实身份与有效性相同。
- A 能继续处理现有主题版；B 能定位已有生成器和错误；原始源码、实验与候选文件的角色不丢失。
- 跨 Step 的来源摘要、用户约束、Skill 绑定按原授权范围继承。
- 恢复读取到外部覆盖/删除时更新当前状态，历史回执不覆盖现场事实。
- unsafe 副作用不能因新增上下文自动重放；没有新推进条件时保留具体阻塞原因。

放行：注入故障的恢复测试、相关 Multi Runtime 集成测试通过；隔离 Host 重启后显式恢复代表性新 Run，核对恢复事件、Plan revision、实际产物、Assessment 与 Outcome。

回退：撤回恢复输入接入；仍能独立运行此前阶段。历史 Run 不作为反复试验对象。

## 阶段 6：独立建设 Host 自动恢复

前置条件：阶段 5 已证明显式恢复能正确延续任务；另行形成小方案后实施，不与阶段 1—5 合并提交。

范围：Host 持久化扫描、执行权 lease/fence、退避、有限尝试、具体错误记录和耗尽后的终态处理。前端承担状态展示与真实 HIL，不承担唯一调度责任。

放行测试必须覆盖：两个 worker 竞争、Host 重启、超时迟到结果、重复点击、恢复再次失败、耗尽收敛，以及真正需要用户信息时转 HIL。扫描不能形成“恢复的恢复”循环，也不能重复执行已确认的外部副作用。

“继续恢复”按钮链路故障另需独立回归。先前只读调查未实际触发 POST，也没有证明其具体失败原因；缺少后台扫描不能单独解释按钮为何无效。自动调度不能替代对 transport/方法绑定/响应处理的诊断。

## 每阶段统一放行与测试执行

1. 阶段范围内纯函数/fixture 测试；断言事实关系，不只匹配提示词字符串。
2. 脚本化模型/工具的执行集成测试；仅从阶段 3 开始要求模型输入行为验证。
3. 受影响模块的既有回归与构建；阶段 0 固定的基线失败单列，相关失败未解释前不放行。
4. 涉及真实执行/恢复行为的阶段，用隔离 DB、workspace 和端口启动新 Host 验证，记录构建版本；不在实现过程中自动重启用户正在使用的 Host。
5. 保存“改了什么、测试了什么、仍未知什么、如何回退”的阶段验收记录，再进入下一阶段。

现有命令入口（工作区根目录；按阶段选择受影响测试，不在每阶段盲目跑全部）：

```sh
node --test --test-isolation=process packages/agentloop/tests/execution-context-policy.test.ts packages/agentloop/tests/step-execution-strategy.test.ts
node --test --test-isolation=process packages/agentloop/tests/agent-loop.test.ts
node --test --test-isolation=process packages/agentloop/tests/planning-runtime.test.ts
npm run build:kernel
npm run typecheck --workspace agentloop-multi-runtime
npm run test --workspace agentloop-multi-runtime
```

跨包验证前先构建 Kernel，避免链接到旧 dist。新增纯状态测试的文件名、精确命令及已执行结果见对应阶段验收记录；本节仅列通用入口，不代表每个阶段已执行所有命令。

任何阶段出现以下情况即停止扩大范围：测试产物被误当交付物；旧版本检查被用于新版本；空回复抹掉已有成果；上下文体积显著膨胀且无明确收益；引入 Run/业务特例；必须同时改规划、验收与调度才能通过该阶段测试。
