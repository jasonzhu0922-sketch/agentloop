# 交付目标生命周期

交付目标属于 Run；Plan Step 负责生产或采用交付物，步骤的调度生命周期不决定交付物的存续。

## 统一链路

`冻结意图 → canonical targets → Step ownership → candidate claims → Assessment → accepted realization → 最终交付`

- 意图确定交付目标清单、交付面及数量；步骤只引用目标 ID。文件和对话目标可以属于同一步骤。
- Candidate 按步骤拥有的完整 canonical 清单生成声明。非空对话内容产生对话声明；文件声明必须对应当前版本绑定及该路径、摘要的验收回执。文件观察器不负责推导对话目标。
- Assessment 分别判断各目标是否满足原请求。步骤整体未通过时，已经通过且具备有效声明的目标仍然可以独立验收。
- Canonical target 保存已验收实例：原生产步骤、Assessment、证据引用，以及对话正文或文件版本绑定。步骤退役只停止后续调度，不删除这些记录。

## 规划与恢复

`需要覆盖的交付义务 = 已验收且当前有效的实例 + 尚未完成目标的生产步骤`

Admission 和 Recovery Planner 使用同一 `canonicalDeliveryPlanScope`。新步骤必须恰好覆盖未完成目标，不能重新分配已验收目标。已完成步骤按持久化 ID 保留；部分完成的混合步骤可以退役，由新步骤仅接管未完成目标。文件生产步骤可以位于最终对话步骤之前。

## 失效与最终交付

- 交付绑定的文件发生后续写入、删除、内容变化或存在相互冲突的观察时，旧验收失效，目标及对应 GoalGap 重新打开。保留历史验收记录以供审计。
- 新写入缺少摘要时不能沿用旧验收；相同内容的重写仍然是新的文件实例。读取同一内容不撤销验收。
- 用户修改意图通过独立的 canonical intent 修订使旧交付义务失效。
- 最终输出从终点步骤输出与 Run 的有效验收记录生成，补齐此前已验收的对话正文和文件链接；不依赖原步骤是否仍然活跃，也不重新调用模型改写已验收内容。

回归见 `packages/agentloop/tests/delivery-target-lifecycle.test.ts`：混合交付、两种部分失败恢复、分步交付、禁止遗漏或重分配目标，以及跨步骤的文件变更与读取。
